# Susanin UI / Tunnels Performance — acceptance review

Дата: 2026-09-22  
Проверяемый отчёт: `reports/susanin/SUSANIN_UI_TUNNELS_PERFORMANCE_REMEDIATION_REPORT_2026-09-22.md`

## Вердикт

**НЕ ПРИНЯТО. Gates G/H закрыты преждевременно.**

В рабочем дереве действительно есть полезные изменения интерфейса Susanin, ленивой загрузки вкладок и кэширования списка туннелей. Целевые frontend-тесты проходят. Однако отчёт завышает степень готовности:

1. backend-тесты были только скомпилированы через `go test -c`, но не запущены;
2. фактический запуск `internal/api` падает;
3. заявленное разделение inventory/runtime Mihomo не доведено до отдельных потоков загрузки;
4. ускорение в 8–10 раз и один начальный запрос не подтверждены сохранёнными измерениями на роутере;
5. показанный после деплоя интерфейс proxy-групп визуально сломан;
6. новые компоненты Susanin добавили предупреждения доступности.

Сборка IPK, установка и изменение конфигурации роутера в рамках этого аудита не выполнялись.

  - заголовок `Server-Timing` для представления туннелей;
  - переработанный экран Susanin.

## Блокирующие замечания

### P0. Backend acceptance фактически не пройден

Команда:

```text
wsl.exe -d Ubuntu -- bash -lc "cd /mnt/e/AWGM/awg-manager && go test -count=1 ./internal/adaptiverouting ./internal/api"
```

Результат:

- `./internal/adaptiverouting` — PASS;
- `./internal/api` — FAIL.

Падения:

```text
TestAdaptiveRoutingHandler_GetAndPutSettings
PUT status 400 instead of 200
подготовка ipset: fork/exec /opt/sbin/ipset: no such file or directory

TestAdaptiveRoutingHandler_LearnedAndForget
POST clear cache status 500
```

Причина: handler-тесты создают реальный `adaptiverouting.Service`, который пытается выполнить `/opt/sbin/ipset`. Тесты не изолированы от окружения роутера.

Обязательное исправление:

- выделить datapath/executor/ipset backend в интерфейс;
- внедрять его в `adaptiverouting.Service`;
- в unit/handler-тестах использовать fake/no-op реализацию;
- после исправления реально выполнить, а не только скомпилировать:

```text
go test -count=1 ./internal/adaptiverouting ./internal/api
go test -race -count=1 ./internal/adaptiverouting ./internal/api
```

### P0. Визуальное исправление proxy-групп не принято на роутере

На представленном после деплоя экране карточки и область proxy-групп почти полностью чёрные, текст имеет недостаточный контраст. Это противоречит утверждению отчёта «тема исправлена».

Рабочее дерево могло измениться позднее установленного IPK, поэтому по одному скриншоту нельзя утверждать, что текущий исходник всё ещё содержит ту же ошибку. Но нельзя и принимать исправление без проверки именно собранного артефакта.

Обязательная проверка:

- собрать frontend из текущего дерева;
- записать commit/digest сборки;
- проверить светлую и тёмную темы на desktop и mobile;
- проверить computed styles карточки, фона, текста, badge и controls;
- сохранить скриншоты и браузерную консоль;
- исключить старые asset-файлы и несоответствие HTML ↔ hashed JS/CSS после обновления.

## Высокий приоритет

### P1. Разделение Mihomo inventory/runtime осталось внутренним рефакторингом

В `mihomoNative.ts` появились отдельные функции получения inventory и runtime, но подписываемый `mihomoNativeResources` по-прежнему собирает полный snapshot и выполняет пять запросов: три inventory и два runtime.

Следствие: открытие вкладок подписок/групп всё ещё может запускать runtime-запросы, хотя для их первого отображения достаточно inventory.

Нужно:

- создать отдельные stores/pollers для inventory и runtime;
- вкладкам подписок и групп подписываться только на inventory;
- runtime загружать лишь для карточек/экранов, где нужны состояние, задержка и активный узел;
- останавливать polling сразу после ухода с вкладки;
- добавить тест числа запросов при первом входе и переключении вкладок.

### P1. Timeout кэша не является жёсткой гарантией времени ответа

`context.WithTimeout` ограничит работу только функций, которые корректно реагируют на отмену контекста. После запуска параллельных вызовов код ожидает `WaitGroup`. Если provider зависнет или проигнорирует `ctx`, обработчик продолжит ждать после 1500 мс.

Нужно:

- обеспечить подтверждённую поддержку context cancellation всеми provider-вызовами; либо
- отделить ожидание результата от зависшего worker через канал и жёсткий deadline;
- не допустить неограниченного накопления зависших goroutine;
- добавить тест provider-а, игнорирующего context.

### P1. Возможен stampede при холодном или истёкшем кэше

Несколько одновременных запросов могут одновременно начать одинаковое обновление. Нужен singleflight/эквивалентная синхронизация с одним refresh на ключ кэша и общей stale-копией для остальных запросов.

Добавить тест с 20–50 конкурентными запросами и проверкой, что provider вызван один раз.

### P1. Заявленные метрики производительности не доказаны

В отчёте указаны `<40 ms`, `1 request`, `180–320 ms`, `<5 ms` и ускорение `8–10x`, но не приложены:

- HAR/Network trace до и после;
- реальные значения `Server-Timing` с роутера;
- команды и сырой вывод замеров;
- холодный/тёплый сценарий;
- статистика нескольких повторов.

До появления воспроизводимых измерений эти числа следует считать оценочными, а не acceptance evidence.

Минимальная матрица:

1. первый вход на «Туннели», холодный backend-кэш;
2. повторный вход, тёплый кэш;
3. переход AWG → Подписки → Группы → AWG;
4. медленный/недоступный внешний provider;
5. 10 параллельных открытий `/api/tunnels/all`;
6. замер на обоих целевых роутерах.

## Средний приоритет

### P2. Предупреждения доступности в SusaninAdaptiveTab

`svelte-check` сообщил 128 предупреждений в проекте; в новом `SusaninAdaptiveTab.svelte` выявлено не менее 11 предупреждений о label/control association (районы строк 470, 706, 716, 726, 768, 783, 830, 839, 848, 857, 866).

Нужно связать `label for` с `id` либо использовать корректную вложенность, затем добавить keyboard/focus smoke-test.

### P2. Не доказано полное покрытие инвалидирования

Инвалидирование кэша добавлено в NDMS hook, но acceptance должен подтвердить все источники изменения состава туннелей: создание, изменение, удаление, импорт, запуск/остановка и внешние изменения. После каждой операции список не должен оставаться устаревшим до TTL.

### P2. Возвращаемые кэшированные структуры должны быть защищены от мутации

Проверить, что срезы/элементы кэша копируются на границе чтения и записи либо гарантированно immutable. Добавить race-тест параллельного чтения, refresh и invalidation.

## Обязательный порядок исправления

1. Сделать `adaptiverouting` тестируемым через внедряемый datapath/executor и добиться PASS реальных Go-тестов.
2. Разнести inventory/runtime на самостоятельные frontend stores и доказать число запросов тестами.
3. Закрыть hard-timeout и singleflight для snapshot cache.
4. Добавить concurrency/race/cache-copy/invalidation тесты.
5. Исправить a11y предупреждения нового Susanin UI.
6. Собрать артефакт с идентификатором исходников и проверить тему proxy-групп.
7. Выполнить браузерные и router performance measurements с сохранёнными доказательствами.
