# Susanin UI и первая загрузка «Туннелей»: план исправлений

**Дата аудита:** 2026-09-22  
**Репозиторий:** `E:\AWGM\awg-manager`  
**Ветка:** `feature/mihomo-ai-proxyrt`  
**Основание:** визуальная проверка версии `2.17.63`, `SUSANIN_ADAPTIVE_ROUTING_PROGRESS_REPORT_2026-09-22.md`, фактический код рабочей директории.

## Вердикт

Gate G и Gate H нельзя считать завершёнными на 100%. Backend-каркас Susanin присутствует, но пользовательский интерфейс пока не соответствует существующему AWG Manager, вкладка proxy-групп имеет явную регрессию светлой темы, а первая загрузка страницы «Туннели» построена вокруг слишком тяжёлого блокирующего критического пути.

Этот документ является **заданием на реализацию**, а не предложением подготовить ещё один план. Агент должен внести исправления, тесты и выдать один итоговый walkthrough с измерениями до/после.

## P0. Исправить сломанную тему вкладки «Прокси-группы»

### Подтверждённая причина

`frontend/src/lib/components/tunnels/ProxyGroupsTabSection.svelte` использует Tailwind arbitrary values с переменными, которых нет в действующей теме AWG Manager:

- `--surface-bg` с fallback `#161b22`;
- `--surface-bg-subtle` с fallback `#0d1117`;
- `--border`, `--border-subtle`, `--border-hover`;
- `--fg` с fallback `#c9d1d9`;
- жёсткие dark-only классы `bg-blue-950/70`, `text-blue-300`, `text-blue-400`.

В светлой теме срабатывают именно тёмные fallback-значения, что полностью совпадает со скриншотом. Компонент также импортирует неиспользуемые `onMount`, `Card`, `Shield`.

### Требуемое исправление

1. Удалить все собственные GitHub-dark fallback-цвета.
2. Использовать только существующие токены AWG Manager:
   - `--color-bg-secondary`;
   - `--color-bg-tertiary`;
   - `--color-bg-hover`;
   - `--color-border` / `--color-border-hover`;
   - `--color-text-primary`, `--color-text-secondary`, `--color-text-muted`;
   - `--color-accent`, `--color-accent-tint`, `--color-success`, `--color-error`.
3. Лучше не дублировать карточную систему вручную: использовать `Card`, `Button`, `Badge`, существующие паттерны карточек Mihomo и `tunnel-layout.css`.
4. Проверить обе темы и ширины 360, 768, 1280 и 1920 px.
5. Карточка группы должна иметь нормальные отступы, читаемый заголовок, один компактный блок текущего узла, переносимые chips и видимые действия без переполнения.
6. Удалить неиспользуемые импорты и добавить component test хотя бы на рендер групп, пустое состояние и выбор участника.

### Критерий приёмки

- На светлой теме нет почти чёрных областей и текста с недостаточным контрастом.
- На тёмной теме нет жёстко прибитых цветов, конфликтующих с темой.
- Визуально вкладка является частью страницы «Туннели», а не отдельным чужим интерфейсом.

## P0. Убрать тяжёлые запросы из критического пути первого открытия «Туннелей»

### Подтверждённые причины

#### 1. Общий скелетон ждёт два независимых ресурса

В `frontend/src/routes/+page.svelte` переменная `loading` остаётся истинной, пока не готовы одновременно:

- глобальный `/api/system/info`;
- первый снимок `/api/tunnels/all`.

Системная информация не нужна для показа вкладок и уже загружается глобально. Она не должна блокировать основное содержимое страницы.

#### 2. При входе запускаются данные всех вкладок

`+page.svelte` сразу подписывается на:

- `tunnels`;
- `singboxStatus`;
- `singboxTunnels`;
- `awg3Tunnels`;
- `mihomoNativeResources`;
- поток traffic.

Это происходит независимо от активной вкладки. В итоге роутер одновременно обслуживает несколько тяжёлых запросов, хотя пользователь сначала видит только AWG или ранее выбранную вкладку.

#### 3. Один снимок Mihomo сам состоит из пяти запросов

`frontend/src/lib/stores/mihomoNative.ts` выполняет `Promise.all` для proxies, subscriptions, groups, runtime proxies и providers. Даже для вкладки proxy-групп или для подсчёта badge загружается весь набор runtime/provider данных.

#### 4. `/api/tunnels/all` ждёт самые медленные источники

`internal/api/snapshot.go` запускает managed, external и system списки параллельно, но затем делает общий `wg.Wait()`. Для external и system установлен timeout по 4 секунды. Поэтому один медленный NDMS/system вызов удерживает весь первый снимок и весь экран-скелетон до четырёх секунд.

#### 5. Нет измерений длительности стадий

Отчёт агента показывает функциональные PASS, но не содержит browser waterfall, Server-Timing, p50/p95 или хотя бы длительности `/api/tunnels/all`. Утверждение о завершённом Gate H поэтому не покрывает наблюдаемую пользователем проблему.

### Требуемая frontend-архитектура

1. Убрать `sysInfo` из условия глобального `loading`. После получения tunnel snapshot вывести страницу; зависимые от system info элементы догружаются локально.
2. Рисовать заголовок и tabs немедленно. Скелетон должен быть локальным для контента выбранной вкладки, а не закрывать всю страницу.
3. Подписывать только обязательные stores:
   - `tunnels` — для вкладки AWG;
   - `singboxStatus` и `singboxTunnels` — при выборе туннелей прокси;
   - subscriptions — при выборе подписок;
   - отдельный store групп — при выборе proxy-групп;
   - AWG3 — только при выборе WG endpoints или когда нужен его badge после первого idle-frame.
4. Не загружать runtime providers/proxies ради badge. Разделить `mihomoNativeResources` минимум на:
   - lightweight inventory: counts/groups/proxies/subscriptions;
   - runtime state: только для видимой вкладки;
   - providers: только для UI, где они реально отображаются.
5. Не использовать badge как причину блокирующей загрузки всех разделов. До загрузки показывать badge без числа либо последнее кэшированное число.
6. Сохранить last-good snapshot при навигации между страницами (stale-while-revalidate), чтобы возврат на «Туннели» не возвращал полноэкранный скелетон.
7. Добавить AbortController или generation guard, чтобы завершившийся запрос скрытой вкладки не обновлял уже уничтоженный UI.

### Требуемая backend-архитектура

Предпочтительный вариант — перестать делать `external` и `system` обязательными для первого managed snapshot:

1. `/api/tunnels/all` либо возвращает секции независимо с признаком `loading/stale/error`, либо UI получает managed/system/external отдельными запросами.
2. Медленный NDMS не должен задерживать managed-туннели.
3. Для system/external хранить короткий last-good cache. При timeout вернуть кэш с `stale=true`, а не удерживать или обнулять весь снимок.
4. Добавить ограниченные context timeout для **каждого** источника, включая `listItems`; родительский request context должен корректно отменять дочерние операции.
5. Добавить измерение времени каждой стадии и общий `Server-Timing`, например `managed`, `system`, `external`.
6. Не увеличивать частоту тяжёлого NDMS polling до 5 секунд без доказанной необходимости. Managed runtime можно обновлять часто, inventory системных интерфейсов — заметно реже и по invalidation.

### Минимально допустимый промежуточный вариант

Если разделение API не помещается в один change-set:

- сразу убрать блокировку на `sysInfo`;
- лениво подписывать stores по активной вкладке;
- добавить last-good cache для system/external;
- сократить влияние system/external timeout на первый ответ;
- инструментировать длительности.

Просто уменьшить timeout с 4 секунд без кэша и секционных ошибок **недостаточно**: это ускорит страницу ценой исчезающих карточек.

### Критерии производительности

Проверять на реальном Keenetic, при холодном первом входе и повторном входе:

- каркас страницы и tabs: не более 300 мс после загрузки JS;
- первая полезная секция из кэша: не более 500 мс;
- managed AWG cards на LAN: целевой p95 не более 1 секунды;
- зависший NDMS/system источник не скрывает managed cards;
- переход между уже посещёнными вкладками не показывает полноэкранный скелетон;
- одновременно на первом входе не стартуют запросы данных всех скрытых вкладок.

В walkthrough приложить browser Network waterfall и таблицу `endpoint / before / after / cache state`.

## P1. Переработать Susanin UI, сохранив существующий дизайн AWG Manager

### Что сейчас неудачно

- hero занимает много высоты и дублирует действия;
- шесть равнозначных счётчиков перегружают первый экран;
- три карточки растягиваются до одинаковой большой высоты, хотя содержимого в первой существенно меньше;
- важные поля и подписи слишком узкие, текст переносится случайно;
- кнопки «Применить», «Запустить», «Изученные направления», «Экспертный режим» визуально не образуют ясный workflow;
- интерфейс рассказывает внутреннюю реализацию (`conntrack`, SYN-ACK, ipset) до того, как пользователь выбрал базовый сценарий;
- нет явного состояния «есть несохранённые изменения» и различия «сохранить настройки» / «запустить движок».

### Целевая структура

1. **Компактная status bar:** состояние, routing owner, выбранный выход, fail policy; справа одно основное действие Start/Stop и вторичное Apply только при dirty state.
2. **Обычная настройка в две колонки или последовательные строки:**
   - Источник трафика;
   - Выход;
   - Поведение при недоступности.
3. Детектор с разумными defaults показывать как готовый пресет (`Сбалансированный`) и раскрывать параметры по кнопке «Настроить детектор».
4. Статистику обучения вынести ниже в отдельную секцию с TCP/UDP, тестируемыми и изученными направлениями; не занимать ей hero.
5. Expert-раздел сделать настоящим accordion/drawer и оставить закрытым по умолчанию.
6. Системные fwmark/table ID показывать read-only; редактирование — только после отдельного подтверждения developer override.
7. Использовать существующие `PageHeader`, `Card`, `StatStrip`, `FormRow`, `Dropdown`, `Button`, `Badge`, spacing и breakpoints проекта.
8. На ширине, где три колонки становятся тесными, переходить сначала в две, затем в одну; не ждать только порога 900 px для схемы 3→1.

### UX-семантика

- `Применить` сохраняет и атомарно применяет настройки; кнопка показывается активной только при dirty state.
- `Запустить` недоступна без валидного выбранного egress и успешного preflight.
- Проверка выхода должна показывать не только interface, но и тип (`system tunnel`, `Mihomo group`, `sing-box outbound`) и причину недоступности.
- При ошибке применения сохраняется прежняя рабочая конфигурация и отображается понятный rollback result.
- Термины «Mihomo proxy-group» и «sing-box individual/composite outbound» не смешивать.

## Обязательный порядок реализации

1. P0 theme regression proxy-групп.
2. Инструментирование времени запросов и воспроизводимый baseline.
3. Удаление `sysInfo` из глобального loading и секционные skeleton/error states.
4. Lazy subscriptions по активной вкладке.
5. Разделение Mihomo inventory/runtime store.
6. Независимый/cached backend snapshot для managed/system/external.
7. Перекомпоновка Susanin UI.
8. Автотесты, измерения на роутере, итоговый walkthrough.

## Запреты и границы

- Не собирать и не устанавливать IPK в рамках исправления без отдельного разрешения пользователя.
- Не использовать `--force-reinstall` и не выполнять скрытые destructive cleanup.
- Не менять Wireguard2 `51820`, mixed-port Mihomo `1099` и действующие пользовательские маршруты.
- Не объявлять gate закрытым только по `npm run check`: требуется визуальная проверка обеих тем и измерение реальной первой загрузки.
- Не переписывать unrelated dirty-tree файлы и не удалять пользовательские scratch/report материалы.

## Definition of Done

Работа завершена только когда одновременно выполнены все условия:

- proxy-группы корректны в светлой и тёмной теме;
- Susanin визуально согласован с остальным AWG Manager и имеет понятный основной сценарий;
- cold-load «Туннелей» измерен и ускорен;
- скрытые вкладки не создают тяжёлый стартовый burst запросов;
- медленный system/NDMS источник не блокирует managed cards;
- тесты проходят, `git diff --check` чист;
- итоговый walkthrough содержит список изменённых файлов, тесты, waterfall и before/after timings, а не очередной план.
