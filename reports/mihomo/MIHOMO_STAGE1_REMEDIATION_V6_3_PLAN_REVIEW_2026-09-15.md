## Вердикт

**План v6.3 пока нельзя отдавать в реализацию без правок.** Он правильно охватывает все прежние направления замечаний, но содержит несколько технически неверных или неполных решений. Если реализовать его буквально, часть новых тестов либо не проверит заявленную гарантию, либо будет нестабильной, а OpenAPI снова разойдётся после обычного `go generate`.

После устранения обязательных пунктов ниже план можно запускать в работу. Код, IPK и роутеры в рамках этого ревью не изменялись.

## Что исправлено в концепции правильно

1. Предложена строгая проверка полей manifest до построения путей.
2. Версия Mihomo извлекается только после имени продукта, а не из любого semver-подобного фрагмента вывода.
3. Предлагается сохранять quarantine и использовать `mktemp -d`.
4. Verifier переводится с проверки наличия действий на проверку последовательности событий.
5. Проверка OpenAPI должна охватывать backend- и frontend-копии.
6. Для каждого отклонённого запроса планируется отдельная перезагрузка store с диска.
7. Walkthrough должен содержать только фактический вывод команд.

## Обязательные исправления плана

### P1. Ошибка Python в process substitution не должна теряться

План предлагает встроить validation в существующую конструкцию:

```bash
{ read ...; } < <(python3 ...)
```

Код возврата процесса внутри `< <(...)` не является надёжным статусом основной команды shell. Нельзя строить гарантию fail-closed только на `set -e` и ожидать, что любая ошибка Python обязательно будет обработана корректно.

Нужно явно запустить parser/validator в foreground и проверить его код возврата. Например:

1. создать временный файл внутри уже безопасно созданного временного каталога;
2. `python3 ... > "$fields_file"` как отдельную команду;
3. проверить exit code;
4. прочитать ровно 11 NUL-delimited значений;
5. проверить отсутствие двенадцатого значения и отсутствие хвоста.

Ещё лучше вынести validator в отдельный Python-файл с unit-тестами. Запрещено строить `CACHE_DIR`, `LOCK_FILE` или пути назначения до успешной валидации.

### P1. Правила manifest должны быть точными и непротиворечивыми

В плане написано «все 11 ключей», но реально валидируются 11 конечных значений, включая вложенные поля. Нужно перечислить точные JSON paths и типы.

Добавить требования:

- root, `binary`, `geodata`, а также каждый объект ресурса должны быть JSON objects;
- строка после trim не пустая;
- `assetName` — только basename, не `.` и не `..`, без `/`, `\\`, NUL и управляющих символов;
- URL после parsing имеет scheme `https`, непустой host, отсутствуют credentials и fragment;
- `http` разрешается только в тестовом режиме, причём флаг должен приниматься строго как `1`;
- SHA-256 нормализуется в lowercase или сравнивается без неоднозначности;
- version соответствует выбранной политике SemVer.

Текущий план одновременно называет формат semver-подобным и намеренно разрешает `v01.19.29`. Это не SemVer 2.0.0. Следует либо запретить leading zeros, либо явно назвать формат собственным и добавить одинаковое правило в manifest validator и Go matcher.

### P1. Публикация cache и восстановление quarantine всё ещё не транзакционны

Предложенный код делает:

```bash
mv "$CACHE_DIR" "$QUARANTINE_DIR"
mv "$STAGING_DIR" "$CACHE_DIR"
...
mv "$QUARANTINE_DIR" "$CACHE_DIR" 2>/dev/null || true
```

Проблемы:

- ошибка первого `mv` отдельно не диагностируется;
- ошибка восстановления подавляется через `|| true`, хотя это и есть состояние recovery required;
- не задано поведение, если имя quarantine уже существует;
- timestamp в секундах плюс PID не является достаточным контрактом для повторного процесса с тем же PID/пространством имён;
- после успешного `mv` trap снимается, но переменная всё ещё указывает на уже перемещённый staging; это безопасно лишь случайно и должно быть оформлено явно;
- не проверяется, что cache root и все вычисленные пути остаются внутри разрешённого root после canonicalization.

Нужно задать state machine публикации: `prepared -> old_quarantined -> committed` и явный recovery outcome. Ошибка restore не должна маскироваться. Для quarantine использовать `mktemp -d`/атомарно зарезервированное уникальное имя в том же parent filesystem.

### P1. Scenario 13 не проверяет rollback после точки quarantine

«Создать файл по пути cache dir, чтобы сломать mv» ломает публикацию до существования корректно quarantined directory и не доказывает восстановление прежнего cache после второго `mv`.

Нужен детерминированный failpoint именно между:

1. успешным переносом прежнего cache в quarantine;
2. неуспешной публикацией staging.

Допустимые варианты: test-only env failpoint в скрипте или контролируемый wrapper для `mv`, считающий вызовы. Acceptance должен проверить:

- ненулевой exit;
- прежний cache восстановлен byte-for-byte;
- staging не опубликован частично;
- если restore искусственно ломается, скрипт сообщает recovery-required и сохраняет quarantine.

### P1. Scenario 14 с «shadow missing binary» в текущем виде неработоспособен

Нельзя «затенить команду отсутствующим бинарником»: `command -v` продолжит поиск по следующим каталогам PATH. План должен описать воспроизводимый механизм:

- либо отдельный test-only список/tool resolver;
- либо изолированный PATH с symlink/wrapper для всех требуемых команд, кроме проверяемой;
- либо запуск в минимальном контейнере/окружении.

Также preflight должен включать реально используемые внешние команды (`awk`, `chmod`, `mv`, `mkdir`, `rm`, `touch` и другие после финального refactor), а не только шесть выбранных утилит.

### P1. OpenAPI post-processing не подключён к источнику истины и CI

Фраза «script should be called from `go generate` or Makefile» оставляет ключевое решение неопределённым. В текущем репозитории:

- `cmd/awg-manager/docs.go` запускает только `swag init`;
- CI проверяет свежесть `internal/openapi/swagger.yaml` сразу после `go generate ./cmd/awg-manager`;
- frontend имеет `sync:openapi`, а также отдельную генерацию `schemas.gen.ts`.

План обязан выбрать и описать одну реальную цепочку. Минимально:

1. добавить второй `//go:generate` для patcher после `swag init` либо wrapper-generator, выполняющий оба шага;
2. синхронизировать `frontend/static/openapi.yaml` штатной командой, а не скрытым copy с неясной ответственностью;
3. после патча запустить генерацию `frontend/src/lib/api/schemas.gen.ts`;
4. обновить CI так, чтобы он проверял все три артефакта;
5. проверить идемпотентность и отсутствие diff после полного pipeline.

Просто патчить YAML вручную после `go generate` недостаточно.

### P1. Verifier должен проверять полный lifecycle пакета

Предложенный автомат конечных событий улучшает ситуацию, но остаются пробелы:

- `state` фактически не переводится в `TERMINAL`;
- события после terminal безусловно разрешаются;
- отсутствие package-level terminal сейчас принимается;
- несколько package terminal events не отклоняются;
- не проверяется, что package соответствует package целевого теста;
- неизвестные action молча принимаются.

Нужно определить два автомата: target test и его package. Требовать ровно один test `run`, ровно один test terminal `pass`, затем ровно один package terminal `pass`; отклонять test events после terminal и конфликтующие terminal events. Разрешённые служебные actions перечислить явно.

Добавить сценарии: package terminal отсутствует; duplicate package terminal; package pass до test terminal; события одноимённого теста из другого package; output после terminal; неизвестный action.

### P2. Bash-проверка quarantine небезопасна для путей

Конструкция `QUARANTINE_DIRS=($(find ...))` ломается на whitespace/globbing. Использовать `mapfile -d ''` вместе с `find -print0`, проверить ровно ожидаемое количество директорий и выбирать созданную текущим запуском по сохранённому пути/логу, а не «последний элемент» неупорядоченного `find`.

### P2. Per-error persistence test должен сравнивать полное сериализованное состояние

Ручное сравнение пяти полей может пропустить новые поля структуры и различия порядка/metadata. Нужно:

- прочитать исходный файл bytes до операции;
- после отклонения сравнить bytes или canonical JSON;
- создать новый Store из того же файла;
- сравнить полный deep snapshot;
- каждый subtest должен иметь собственный `t.TempDir()` и не переиспользовать состояние.

План также должен указать, как helper легально сохраняет unsupported rules. Если он обходит production API прямой записью, нужно отдельно проверить корректность fixture.

### P2. Набор manifest tests недостаточен

Добавить table-driven отрицательные варианты как минимум для каждого класса:

- wrong type (`null`, number, array, object вместо string);
- пустая/whitespace-only строка;
- `assetName` равен `.` или `..`, содержит backslash/control char;
- version с `/`, `\\`, `..`, leading zero согласно принятой политике, build metadata;
- SHA слишком короткий/длинный/non-hex;
- URL без host, с credentials, fragment, `file://`;
- лишнее NUL-поле/неполный вывод parser;
- cache root с пробелом.

Проверка traversal обязана утверждать не только отсутствие одного `target`, а неизменность snapshot всего каталога вне test cache.

### P2. Политика quarantine не должна блокировать реализацию

Для Stage 1 достаточно правила: bootstrap никогда автоматически не удаляет quarantine. `--prune-quarantine` — отдельная будущая функция, не включать её в текущий remediation без отдельного контракта retention/age/locking/dry-run. Это снимает первый вопрос из `User Review Required`.

1. Зафиксировать формальные контракты manifest, version и cache path.
2. Вынести foreground manifest validation и покрыть table-driven тестами.
3. Реализовать безопасный staging и транзакционную публикацию с failpoints/recovery tests.
4. Исправить anchored version matcher и его positive/negative tests.
5. Реализовать test/package event state machines и расширить self-tests.
6. Выбрать единый OpenAPI generation pipeline, встроить patcher и обновить CI/artifacts.
7. Усилить per-error disk persistence tests полным сравнением состояния.
8. Выполнить целевые тесты, race, bootstrap, verifier, OpenAPI, frontend и `git diff --check`.
9. Только после фактического успешного прогона переписать walkthrough реальным выводом.

## Критерии допуска к повторному аудиту

- Все требования плана сформулированы однозначно, без `or`, `should` и незакрытых пользовательских решений.
- Ошибка parser наблюдается основным shell process и гарантированно прекращает выполнение до создания path/lock/cache.
- Publication-failure test действительно ломает второй переход после quarantine и доказывает restore.
- Recovery failure не подавляется.
- Missing-tool test воспроизводимо проверяет именно preflight.
- Verifier требует завершённый successful lifecycle теста и пакета.

- Backend YAML, frontend YAML и generated TypeScript согласованы.
- Каждый rejected delete case доказывает неизменность файла после повторного открытия store.
- Walkthrough содержит фактические команды, правильное имя acceptance test и реальные exit codes.
