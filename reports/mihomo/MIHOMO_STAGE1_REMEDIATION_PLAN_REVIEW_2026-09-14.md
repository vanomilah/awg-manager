## Вердикт

**Условно одобрено после обязательной корректировки плана.**

Новая редакция закрывает основную часть повторного аудита: предлагает единый backend-registry правил, корректно отказывается от неподдерживаемого `SUB-RULE`, добавляет проверки ссылок provider/DNS, уникальности listener'ов и прекращает подавлять ошибки JSON в router adapter.

Однако запускать план как окончательный пока нельзя. В нём осталось два функционально опасных пункта и несколько неполных критериев приёмки. Если реализовать текст буквально, валидные DNS-конфигурации Mihomo могут начать отклоняться, а расхождение между backend и UI появится снова при следующем добавлении типа правила.

## Обязательные исправления до запуска

### P0. Проверка DNS `#detour` описана неверно

В плане предлагается проверять любой `#<detour>` через `validRuleTarget`. Это несовместимо с синтаксисом Mihomo.

После `#` допускается не только имя proxy/group:

- специальное значение `RULES`;
- имя существующего proxy или proxy-group;
- имя сетевого интерфейса;
- дополнительные параметры, соединённые через `&`, например `ecs=...`, `skip-cert-verify=true` и другие.

Официальная документация: <https://wiki.metacubex.one/en/config/dns/#dns-specifies-proxyinterface-for-connection>

Нужно заменить пункт 36–37 плана следующим контрактом:

1. Реализовать отдельный parser/validator DNS server URI, не переиспользовать `validRuleTarget` напрямую.
2. Разобрать fragment по `&`; только первый безымянный selector может быть маршрутом.
3. `RULES` принимать как встроенное значение без учёта регистра и нормализовать в `RULES`.
4. Известное имя proxy/group принимать.
5. Произвольное имя интерфейса не отклонять статически, если проект не располагает достоверным каталогом интерфейсов на этапе компиляции.
6. Именованные параметры (`ecs=`, `ecs-override=`, `h3=`, `skip-cert-verify=` и т.п.) не трактовать как outbound.
7. Добавить тесты минимум для `#Group`, `#RULES`, `#eth3`, `#Group&ecs=1.1.1.0/24`, неизвестного параметра и malformed fragment.

Также текущий тип `DNS.NameserverPolicy map[string]string` не поддерживает документированный массив DNS-серверов. Это не обязательно исправлять в Stage 1, но ограничение нужно явно записать, иначе формулировка «полный grammar contract» неверна.

### P0. Frontend не подключён к единому registry

План создаёт единый источник истины только для `internal/mihomo` и `internal/mihomonative`, но оставляет самостоятельный массив `ruleTypes` в `MihomoPolicyPanel.svelte`. Удаление одного `SUB-RULE` вручную не устраняет исходную причину рассинхронизации.

Нужно выбрать один из вариантов:

- предпочтительно: backend endpoint/capability schema возвращает поддерживаемые rule specs, а UI строит список из него;
- допустимо для Stage 1: генерируемый TypeScript-контракт плюс тест parity, который падает при несовпадении frontend/backend;
- минимально допустимо: отдельный frontend contract-test со всеми 36 поддерживаемыми типами и явной проверкой отсутствия `SUB-RULE`.

Без этого нельзя заявлять «Single Rule Registry» для всей функции.

## Существенные уточнения

### P1. `RuleSpec` должен описывать реальную грамматику, а не только минимум полей

Поля `MinFields`, `TargetIndex` и `RequiresPayload` недостаточны для строгой проверки:

- `MATCH` имеет другую позицию target;
- `no-resolve` допустим не для каждого типа;
- логические `AND`, `OR`, `NOT` содержат вложенное выражение;
- `RULE-SET` требует существующий rule-provider;
- лишние поля и неверно расположенные модификаторы также должны диагностироваться.

Добавить в `RuleSpec` или эквивалентную validation-функцию:

- допустимый диапазон arity;
- разрешённые trailing modifiers;
- специальный validator payload для `RULE-SET` и логических правил;
- нормализатор типа и модификаторов;
- признак поддержки UI.

Если полноценный parser логических выражений не входит в Stage 1, план должен честно назвать эту проверку структурной, а не полной грамматической.

### P1. Проверка конфликтов listener'ов не должна сравнивать только номер порта

Одинаковый номер порта не всегда означает конфликт: важны bind address и транспорт сокета. При этом wildcard-bind конфликтует с конкретным адресом, а top-level proxy ports имеют собственную семантику bind.

Нужно определить endpoint key как минимум из:

- нормализованного адреса (`0.0.0.0`, `::`, loopback, конкретный адрес);
- порта;
- TCP/UDP-capability listener'а.

Для текущей урезанной модели `Listener` можно применить консервативное правило, но оно должно быть явно документировано и покрыто тестами: duplicate name, одинаковый endpoint, разные адреса, TCP против UDP, wildcard против конкретного адреса и конфликт с каждым top-level port.

Документация listener'ов: <https://wiki.metacubex.one/en/config/inbound/>.

### P1. Тест registry может создать import cycle

Если `rules_registry_test.go` останется в пакете `mihomo`, он не сможет импортировать `mihomonative`, когда `mihomonative` начнёт импортировать `mihomo`.

Нужно заранее зафиксировать один из вариантов:

- parity/integration test сделать как `package mihomo_test`;
- либо тест `SaveRule` разместить в `internal/mihomonative`;
- либо вынести общий registry в нейтральный внутренний пакет, если появятся дополнительные потребители.

### P1. Санитизация ошибок должна охватывать весь отображаемый текст

План ограничивает и очищает `Rule` и `Resource`, но `Message` формируется через `fmt.Sprintf` и сейчас нередко повторяет пользовательское значение. Поэтому control characters, чрезмерная длина и чувствительный фрагмент могут попасть в лог через `Message`.

Требуется:

- очищать `Source`, `Resource`, `Rule` и `Message` перед сохранением или перед `Error()`;
- не дублировать raw rule/resource в форматируемом сообщении;
- задать отдельные разумные пределы длины;
- тестировать CR/LF, управляющие символы, очень длинные значения и отсутствие исходного значения после усечения;
- заменить абсолютное утверждение «credentials are never placed» на проверяемый контракт: вызывающий код не должен передавать секреты, а error renderer ограничивает и обезвреживает диагностические значения.

### P1. Provider `proxy` требует строгого разбора динамического значения

Оба provider-раздела представлены как `map[string]map[string]interface{}`. План должен явно потребовать:

- отсутствие `proxy` считать допустимым;
- непустой `proxy` обязан быть строкой;
- строку trim/normalize до проверки;
- разрешать только документированные built-ins и существующие proxy/group;
- неверный тип (`[]any`, число, object) завершать compile fail-closed;
- покрыть это table-driven тестами отдельно для proxy-provider и rule-provider.

### P2. `DynamicCloudCIDRs` не относится к этому remediation pass

Тест из пункта 94–95 полезен только если текущая ветка действительно содержит относящееся к Stage 1 изменение cloud tunnel. Иначе его следует вынести в отдельный коммит/задачу. В walkthrough нужно пояснить происхождение изменения, чтобы remediation Mihomo не маскировал постороннюю функциональную дельту.

## Исправленный порядок реализации

1. Зафиксировать точный поддерживаемый subset правил AWG Manager: 36 типов, а не называть его всеми существующими возможностями Mihomo.
2. Создать backend registry с полноценными validation hooks.
3. Перевести compiler и native store на registry.
4. Связать UI с registry либо добавить строгий parity contract.
5. Удалить `SUB-RULE` из store/API/UI и добавить migration/read-path ошибку для уже сохранённых записей; нельзя допустить тихое исчезновение старого правила.
6. Реализовать provider-reference validation с проверкой динамических типов.
7. Реализовать отдельный DNS fragment parser с поддержкой `RULES`, interface selector и `&`-параметров.
8. Реализовать endpoint-aware проверку listener'ов.
9. Прекратить подавлять marshal/unmarshal errors в router adapter.
10. Сделать полную санитизацию структурированной ошибки.
11. Добавить backend/frontend/integration tests.
12. Только после зелёной приёмки обновлять `walkthrough.md` и переходить к Stage 2.

## Критерии допуска к Stage 2

Stage 1 можно принять, когда одновременно выполнено следующее:

- store, compiler и UI принимают один и тот же набор rule types;
- `SUB-RULE` везде отклоняется явно, включая ранее сохранённые данные;
- все 36 поддерживаемых типов имеют положительный контрактный тест;
- отрицательные тесты проверяют arity, target, payload, modifiers и provider references;
- валидные `#RULES`, `#interface` и `#Group&param=value` DNS URI не отклоняются;
- неизвестные outbound/provider references завершают compile до применения runtime-конфига;
- listener-конфликты определяются по endpoint semantics, а не только по integer port;
- ошибки сериализации не подавляются;
- диагностическая ошибка не допускает log injection и имеет ограниченную длину во всех полях;
- WSL backend tests, frontend checks и representative `mihomo -t` завершаются успешно;
- никаких сборок IPK и деплоя в рамках этой проверки не выполняется.
