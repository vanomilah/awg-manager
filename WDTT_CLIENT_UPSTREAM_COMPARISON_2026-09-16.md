# Сравнение WDTT-клиента: локальная ветка и upstream AWG Manager

Дата проверки: 2026-09-16

## Что сравнивалось

- локальная ветка: `feature/mihomo-ai-proxyrt`, commit `87a563eb4d99011a81f762a9740cd9f1db043b73`;
- актуальный `upstream/develop`: `badc0222655c37cb12518c6c727f51a9f51853cb` (`2.19.2`);
- upstream: <https://github.com/hoaxisr/awg-manager>;
- клиентский бинарь WDTT: форк `hoaxisr/proxy-turn-vk-android`, исходная CLI-часть из `amurcanov/proxy-turn-vk-android`.

Важно: qWDTT для Android и `wdtt-server` на роутере — не тот же объект, что router-side `wdtt-client`. В этом отчёте основное сравнение относится к клиенту, который AWG Manager устанавливает в `/opt/bin/wdtt-client`, и к его интеграции в AWG Manager.

## Короткий вывод

Само транспортное ядро клиента у нас **не является отдельным форком**: каталог `third_party/wdtt-client` побайтно совпадает с актуальным upstream AWG Manager. Обе версии также используют один pinned client `1.4.0-3`.

Главное локальное отличие — новая крупная UI-оболочка WDTT и несколько compatibility-методов. При этом локальная ветка отстаёт от `upstream/develop` на 63 коммита и не содержит свежих исправлений жизненного цикла связанного AWG-туннеля, конфликтов адресов и ряда защит загрузки подписки. Поэтому считать локальный WDTT-клиент функционально «лучше upstream» сейчас нельзя: интерфейс богаче, но backend-интеграция старее.

## Что совпадает

1. Исходники `third_party/wdtt-client` идентичны.
2. Версия устанавливаемого клиентского бинаря идентична: `WdttPinnedClientVersion = "1.4.0-3"`.
3. Основные режимы транспорта задаются тем же клиентом:
   - WG/DTLS;
   - Raw;
   - работа через ссылку/подписку;
   - создание связанного AWG-туннеля для WG-режима.
4. Базовые ProxyRT-роли `wdtt-client` и форматы конфигурации общие.

## Что добавлено только в нашей ветке

### Новый интерфейс WDTT

Локально добавлены отдельные большие компоненты:

- `WdttTab.svelte`;
- `WdttClientSimple.svelte`;
- `WdttServerSimple.svelte`;
- `WdttServerUsers.svelte`;
- `WdttLinkShare.svelte`.

Это примерно 3,2 тыс. новых строк UI. В интерфейсе объединены:

- клиент и сервер WDTT;
- простой мастер настройки;
- WG и Raw;
- DTLS, Direct и Raw-порты;
- ссылки `wdtt://` и qWDTT/QR;
- подписка и её предварительный просмотр;
- связанный AWG-туннель;
- NAT, доступ в LAN, политика доступа;
- маршрутизация входящего трафика через активный proxy-engine;
- управление пользователями сервера и статистикой/логом.

Upstream по-прежнему ведёт `/wdtt` на общий экран `/proxy?tab=exit`; локальная ветка ведёт на собственную вкладку `/?tab=wdtt`.

### Compatibility-слой

Локально сохранены поля и методы для старого standalone WDTT UI/API:

- `password`, `adminId`, `botToken` в `WdttServerConfig`;
- `isMain`, `isExpired`, `isDeactivated`, `deviceCount`, `lastSeenAt` у пользователя;
- `panelDbPath`;
- методы `updateWdttClientConfig()` и `ensureWdttRawTunnel()`.

Это позволяет новому интерфейсу работать со старой моделью данных, но создаёт риск расхождения с текущим ProxyRT-контрактом upstream.

### Локальная очистка при переходе в Raw

Наша версия `EnsureWGTunnel` при режиме Raw отдельно вызывает очистку связанных AWG-туннелей. В текущем upstream эта обязанность перенесена в общий backend-процесс удаления/обновления записи и отдельная ручка очистки удалена.

## Что уже есть в upstream, но отсутствует у нас

### 1. Атомарная привязка создаваемого AWG-туннеля

Upstream импортирует туннель сразу с `clientID`. У нас сначала создаётся туннель, затем отдельным `Update` дописывается `WdttClientID`.

Риск локальной версии: между двумя операциями остаётся окно, в котором туннель существует без связи с WDTT-клиентом. При сбое получается orphan-туннель, который штатная очистка может не найти.

### 2. Проверка конфликта адреса до создания туннеля

Upstream добавил `WDTT_WG_ADDRESS_CONFLICT` и проверку уже занятого адреса. Локальная ветка может создать второй туннель с тем же `/32`, после чего NDMS не сможет его поднять.

### 3. Корректная публикация списка после частичной мутации

Upstream публикует обновлённый список туннелей через единый `defer`, если была любая мутация. В локальной версии публикация привязана в основном к успешным путям. После частично успешной операции UI может показывать устаревшее состояние до перезагрузки.

### 4. Удаление связанных туннелей одним backend-запросом

В upstream удаление WDTT-клиента и его связанных туннелей сведено в один backend lifecycle. У нас фронт сначала вызывает отдельную очистку, затем удаляет инстанс.

Риски локальной версии:

- разрыв между двумя запросами;
- удаление записи после неполной очистки;
- зависимость корректности данных от поведения UI-клиента.

### 5. Защита загрузки подписки

В upstream клиент загрузки подписки дополнительно:

- не наследует HTTP proxy из окружения;
- закрывает keep-alive для одноразового транспорта;
- запрещает downgrade redirect `https -> http`;
- сохраняет SSRF-проверку на реально набираемый адрес.

Локальная ветка использует более старый inline `http.Client` и этих доработок не содержит.

### 6. Новый серверный бинарь

Клиентский pin одинаковый, но upstream уже использует `wdtt-server 1.4.0-5`, а локальная ветка — `1.4.0-4`. Это различие относится к серверу, но способно влиять на совместную работу клиента и выдачу адресов.

### 7. Учёт всех портов WDTT-сервера

В upstream присутствуют исправления коллизий ProxyRT и учёта Raw/Direct-портов WDTT-сервера. В локальной ветке этих последних коммитов нет.

## Практическое сравнение возможностей

| Область | Наша ветка | Upstream автора |
|---|---|---|
| Транспортный WDTT-клиент | Тот же `1.4.0-3` | `1.4.0-3` |
| Собственный экран WDTT | Да, расширенный | Нет, общий ProxyRT UI |
| WG/DTLS | Да | Да |
| Raw | Да | Да |
| Подписка | Да | Да |
| Ссылка/QR/qWDTT | Богатый отдельный UI | Через общий ProxyRT flow |
| Связанный AWG-туннель | Старый двухфазный lifecycle | Атомарная привязка |
| Конфликт адресов | Нет предварительной защиты | Есть `WDTT_WG_ADDRESS_CONFLICT` |
| Удаление связанных туннелей | Два frontend-запроса | Один backend lifecycle |
| Безопасность HTTP-подписки | Старый вариант | Усилена |
| WDTT server pin | `1.4.0-4` | `1.4.0-5` |

## Рекомендация по слиянию

Не заменять нашу WDTT-реализацию целиком upstream-кодом и не удалять новый UI. Правильный путь:

1. Сначала перенести backend-исправления upstream:
   - атомарный `Import(..., clientID)`;
   - `AddressConflicts` и `WDTT_WG_ADDRESS_CONFLICT`;
   - публикацию списка через `defer` после любой мутации;
   - единый backend lifecycle удаления связанных туннелей;
   - защищённый `subscriptionClient`;
   - учёт Raw/Direct-портов;
   - server pin `1.4.0-5` вместе с SHA256 и размерами.
2. Затем адаптировать `WdttClientSimple`/`WdttServerSimple` к новому контракту API.
3. Удалить compatibility-поля только после проверки, что UI больше их не читает.
4. Добавить acceptance-тесты:
   - импорт клиента WG -> туннель сразу связан;
   - повторный адрес -> 409 без созданной записи;
   - удаление клиента -> связанные туннели удалены даже без участия UI;
   - переключение WG -> Raw -> orphan-туннелей нет;
   - сбой запуска после импорта -> список UI всё равно обновлён;
   - redirect подписки `https -> http` отклоняется.

## Итоговый вердикт

Наш «WDTT-клиент» не отличается от клиентского ядра автора протоколом или производительностью: бинарь и vendored source одинаковы. Реальное отличие — расширенный интерфейс и дополнительная интеграция с политиками, Mihomo/Sing-box и серверной частью.

Сейчас преимущество локальной ветки — UX и более широкий экран управления. Преимущество актуального upstream — более зрелый lifecycle, защита от orphan-туннелей/конфликтов адресов и безопаснее реализованная загрузка подписок. Перед дальнейшим тестированием на роутере эти upstream-исправления желательно перенести в нашу ветку.
