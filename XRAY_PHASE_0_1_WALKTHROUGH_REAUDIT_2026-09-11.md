## Блокирующие замечания

### 1. `internal/xrayconfig` не интегрирован в приложение

Поиск по Go-коду показал, что пакет используется только собственными тестами. Следующие компоненты не вызываются из `xrayserver`, API, мастеров или runtime:

- `Compiler` и `CompileWithBase`;
- `Validator`;
- `Redactor`;
- semantic diff.

Следствие: внесённые исправления пока никак не влияют на конфигурацию работающего Xray и не защищают реальный apply.

Необходимо:

1. Импортировать существующий `xrayserver.Config` в управляемую модель.
2. Подключить модель к существующему transaction coordinator.
3. Реализовать pipeline `candidate -> validate -> Xray test mode -> diff -> atomic apply -> readiness -> commit/rollback`.
4. Добавить интеграционные тесты, использующие реальные точки API/runtime, а не только функции пакета.

### 2. Валидатор пропускает нерабочие outbounds

Файл: `internal/xrayconfig/validator.go`, блок проверки outbounds, начиная примерно со строки 227.

Отсутствует обязательная проверка:

- `server` и диапазона `port`;
- обязательного UUID для VLESS/VMess;
- пароля для Trojan и Shadowsocks;
- публичного ключа, server name и short ID для клиентского REALITY;
- совместимости REALITY с протоколом и транспортом outbound;
- обязательного блока TLS при `security=tls`;
- обязательных настроек аутентификации, если они заявлены моделью протокола.

Сейчас UUID проверяется только в том случае, если строка уже непустая. Поэтому компилятор способен сформировать outbound с пустым сервером, портом `0` и пустыми реквизитами.

Нужны отрицательные табличные тесты для каждого поддерживаемого протокола.

### 3. Shadowsocks реализован жёстко и неуниверсально

Файл: `internal/xrayconfig/compiler.go`, строки около 414-426.

Компилятор всегда задаёт:

```text
method = 2022-blake3-aes-128-gcm
```

В модели `Outbound` отсутствует поле cipher/method. Это не позволяет импортировать большинство обычных Shadowsocks-конфигураций. Кроме того, Shadowsocks 2022 предъявляет специальные требования к формату ключа, которые валидатор не проверяет.

Необходимо:

1. Добавить типизированное поле метода шифрования.
2. Ограничить список значений capability matrix установленной версии Xray.
3. Валидировать пароль/ключ в соответствии с выбранным методом.
4. Добавить golden-тесты минимум для legacy AEAD и Shadowsocks 2022.

### 4. `RawSettings` сравниваются не семантически

Файл: `internal/xrayconfig/diff.go`, строки около 209 и 348.

Для `RawSettings` используется побайтовое сравнение `bytes.Equal`. Семантически одинаковый JSON с другим форматированием или порядком ключей будет показан как изменение и приведёт к `restart_required=true`.

Необходимо канонизировать JSON перед сравнением либо сравнивать декодированные структуры. Отдельно нужны тесты на:

- различный порядок ключей;
- пробелы и переносы строк;
- числовые значения;
- массивы, где порядок действительно значим.

### 5. Lossless-контракт остаётся только верхнеуровневым

Файл: `internal/xrayconfig/compiler.go`, `CompileWithBase`.

Сохраняются отдельные верхнеуровневые разделы, но полностью заменяются:

- `inbounds`;
- `outbounds`;
- `routing`;
- `policy`;
- `stats`.

Неизвестные поля внутри управляемых inbound/outbound/routing объектов теряются. Parser, заявленный в общем плане, отсутствует.

До интеграции необходимо реализовать один из двух явных контрактов:

1. AWG Manager полностью владеет управляемыми объектами и предупреждает о потере неподдерживаемых полей.
2. Parser сохраняет opaque-поля каждого объекта и compiler выполняет lossless merge.

Для режима «Эксперт/JSON» предпочтителен второй вариант.

### 6. Не выполнены остальные обязательные части Phase 1

В реализации не обнаружены:

- импорт и миграция текущего `xrayserver.Config`;
- versioned schema migration;
- проверка candidate-файла установленным Xray в test mode;
- интеграция с существующим transaction coordinator;
- защищённое хранилище профилей и секретов;
- capabilities/version matrix;
- интеграционные тесты rollback/readiness;
- доказательство цикла `import -> preview -> export` без потери данных.

## Дополнительные риски

### Стабильная идентичность клиентов

`clientKey` использует fallback `ID -> Email -> UUID -> Remark`. Пустые или повторяющиеся значения могут схлопнуть несколько клиентов в map и скрыть изменения. Валидатор должен требовать уникальный стабильный ID и отдельно обеспечивать уникальность email/UUID там, где этого требует статистика Xray.

### Балансировщики

Routing rule допускает `BalancerTag`, но в управляемой модели нет коллекции балансировщиков и проверки существования указанного balancer. Такой конфиг может пройти внутренний validator и быть отклонён Xray.

### Граница типизированных и raw-настроек

Нужно явно определить приоритет типизированных полей и `RawSettings`. Сейчас наличие `RawSettings` способно заменить protocol settings целиком, а stream settings всё равно формируются из типизированных полей. Без документированного merge-контракта возможны неожиданные потери или противоречия.
