# Оценка EdgeЦентр CDN для Xray XHTTP и Telegram Web Proxy

Дата проверки: 2026-09-11  
Сайт: `https://edgecenter.ru/cdn`

## Краткий вывод

EdgeЦентр технически является самым подходящим из рассмотренных российских CDN-кандидатов:

- поддерживает `GET`, `HEAD`, `POST`, `PUT`, `PATCH`, `DELETE`, `OPTIONS`;
- позволяет полностью отключать кеширование;
- официально поддерживает WebSocket до origin;
- позволяет использовать собственный origin, HTTPS, SNI/Host и собственный домен;
- имеет большое число точек присутствия в России.

Для Xray XHTTP вероятность совместимости высокая. Для Telegram Web Proxy через WebSocket совместимость также вероятна, но WebSocket является подключаемой по запросу опцией и требует передачи данных не реже одного раза в 5–8 секунд.

При этом **принадлежность к «белому списку» подтвердить нельзя**. Единого публичного списка для всех мобильных операторов и тарифов нет. Доступность зависит от конкретного оператора, региона, тарифа, домена, SNI и текущей политики сети. Проверяется только практическими измерениями с SIM-карт нужных операторов в условиях, когда обычный интернет ограничен.

## Кто такой EdgeЦентр

EdgeЦентр — российский оператор CDN, облачной и edge-инфраструктуры. На официальном сайте оператором указан ООО «ЭджЦентр».

Исторически российская инфраструктура связана с бывшей российской частью G-Core Labs. После прекращения деятельности G-Core Labs в России российская команда и мощности продолжили работу под брендом EdgeЦентр.

Это крупная самостоятельная CDN-сеть, а не небольшой виртуальный хостинг. На сайте заявлено более 70 точек присутствия на нескольких континентах, включая большое количество российских площадок.

Источники:

- https://edgecenter.ru/cdn
- https://edgecenter.ru/cdn/tech
- исследование рынка Ростелекома: https://www.company.rt.ru/projects/digital_economy_rf/ncit/files/Развитие_НКИТ_2023.pdf

## Важная связь с уже проверенными продуктами

В документах Cloud.ru CDN используются домены и инфраструктура `edgecenter.ru`, то есть Cloud.ru CDN как минимум технологически связан с EdgeЦентром.

Кроме того, публичные отраслевые сведения указывают, что EdgeCDN распространялся через нескольких реселлеров. Поэтому прямой аккаунт EdgeЦентра может предоставить больше настроек и прямую поддержку, но не обязательно даст другую сетевую инфраструктуру или другую доступность по сравнению с CDN, который уже был заблокирован.

Практическое следствие: EdgeЦентр стоит тестировать, но нельзя заранее считать его независимым новым маршрутом.

## Совместимость с Xray XHTTP

### HTTP-методы

По официальной документации EdgeЦентра по умолчанию доступны:

```text
GET, HEAD, POST, PUT, PATCH, DELETE, OPTIONS
```

Это снимает ограничение старого CDN, где фактически приходилось укладывать транспорт только в GET.

Источник: https://edgecenter.ru/knowledge-base/cdn/http-methods

### Кеширование

Для пути Xray необходимо задать режим «Не кешировать». EdgeЦентр позволяет отключить кеширование CDN для ответов, включая `200`, `206`, `301`, `302`, `4xx` и `5xx`.

Источник: https://edgecenter.ru/knowledge-base/cdn/set-up-cdn-caching

### Origin

Можно использовать собственный IP или домен origin, обращаться к нему по HTTP/HTTPS и настраивать протокол взаимодействия.

Источник: https://edgecenter.ru/knowledge-base/cdn/add-origin-and-pull-protocol

### Предварительный вердикт по XHTTP

| Режим | Оценка |
|---|---|
| XHTTP `packet-up` с GET | Вероятно совместим |
| XHTTP с GET/POST | Вероятно совместим и предпочтительнее искусственного GET-only режима |
| Раздельный upload/download | Требует стендовой проверки таймаутов и буферизации |
| Длинный streaming response | Требует проверки реального idle/origin timeout |
| Несколько путей на одном host | Поддерживается правилами CDN, требуется корректная маршрутизация origin |

Нельзя считать поддержку окончательно подтверждённой только по перечню HTTP-методов. Необходимо проверить отсутствие буферизации, максимальную продолжительность ответа, размер body и поведение chunked/streaming запросов.

## Совместимость с Telegram Web Proxy

EdgeЦентр официально поддерживает WebSocket до origin. Опция активируется через техническую поддержку, после чего включается для CDN-ресурса.

Критическое ограничение документации:

> В открытом WebSocket-соединении данные должны передаваться не реже чем раз в 5–8 секунд, иначе соединение может быть разорвано.

Источник: https://edgecenter.ru/knowledge-base/cdn/websockets

Следствия:

- обычный активный WebSocket-трафик должен работать;
- при простое потребуется корректный application-level ping/pong или heartbeat;
- heartbeat должен быть совместим с клиентом и bridge, а не добавляться как произвольные байты в транспорт;
- после разрыва клиент обязан корректно переподключаться;
- `yac-ws-bridge` либо текущий Telegram Web Proxy нужно проверить на период heartbeat и reconnect.

Для прямого MTProto CDN по-прежнему не подходит. Через CDN может работать только HTTP/WebSocket-обёртка с поддерживаемым клиентом.

## Настройки минимального тестового ресурса

Это не инструкция по обходу сетевых ограничений, а стенд проверки легитимного авторизованного интерактивного сервиса.

Рекомендуемая конфигурация теста:

1. Отдельный тестовый домен, не используемый production-сервисами.
2. HTTPS от пользователя до CDN.
3. HTTPS от CDN до origin с проверкой сертификата и корректным SNI.
4. Два отдельных непересекающихся пути:
   - Xray XHTTP;
   - WebSocket-приложение.
5. Для обоих путей отключить CDN-кеширование.
6. Разрешить только реально используемые HTTP-методы.
7. Запросить у поддержки активацию WebSocket.
8. Не публиковать origin напрямую без firewall/authorization.
9. Включить ограничения доступа, rate limits и наблюдение за кодами ответов.
10. Сначала проверить обычное тестовое HTTP/WebSocket-приложение, затем совместимость целевого транспорта.

## Что уточнить у поддержки до оплаты или переноса

Рекомендуемый нейтральный запрос:

> Планируется авторизованное интерактивное веб-приложение с HTTPS-origin. Нужны некешируемые GET/POST-запросы, streaming/chunked responses и WebSocket. Просим подтвердить максимальные connect/read/send/idle timeout, ограничения размера request/response body, наличие или отсутствие буферизации streaming-ответов, передачу query string и заголовков, а также допустимость длительных двунаправленных соединений. WebSocket-сессия будет использовать heartbeat и авторизацию.

Также необходимо письменно уточнить, допускают ли правила сервиса частный авторизованный транспорт для собственных устройств. Отсутствие найденного публичного запрета нельзя трактовать как явное разрешение.

## Проверка доступности в сетях операторов

### Что можно установить заранее

- У EdgeЦентра много российских точек присутствия и прямых сетевых связей.
- Сервис используется для сайтов, видео и других массовых веб-нагрузок.
- Это повышает общую вероятность нормальной доступности сети CDN.

### Чего нельзя установить по сайту

- входит ли конкретный customer domain в разрешённый список конкретного оператора;
- будет ли разрешён автоматически выдаваемый CDN-домен;
- одинаково ли поведут себя DNS, IPv4 и IPv6;
- не изменится ли политика оператора на следующий день;
- будут ли разрешены WebSocket или долгие HTTP-сессии при доступности обычной страницы;
- не будет ли ресурс административно приостановлен самим CDN.

### Корректный тест

Для каждого нужного оператора отдельно проверить:

1. DNS-разрешение CDN-домена.
2. TCP/TLS-подключение к `443`.
3. Обычный короткий HTTPS GET.
4. Некешируемый GET до origin.
5. POST с небольшим body.
6. Streaming response продолжительностью несколько минут.
7. WebSocket upgrade и обмен сообщениями.
8. Простой WebSocket более 8 секунд и heartbeat.
9. IPv4 и IPv6 отдельно.

Результат действителен только для проверенных SIM, тарифа, региона и времени.

## Риски

1. **Нет гарантии allowlist.** Российская CDN-инфраструктура сама по себе не означает разрешение customer domains.
2. **WebSocket подключается вручную.** Поддержка может запросить описание сценария.
3. **Idle 5–8 секунд.** Без heartbeat Telegram Web Proxy будет нестабилен.
4. **Возможна общая инфраструктура с ранее использованным CDN.** Новый аккаунт может не изменить сетевую доступность.
5. **Административная проверка.** Нет гарантии, что конкретный тип трафика разрешён правилами провайдера.
6. **Origin exposure.** При неправильном firewall клиент сможет обойти CDN и обращаться непосредственно к origin.
7. **Стоимость запросов.** XHTTP с большим количеством мелких запросов может тарифицироваться не только по трафику, но и по числу запросов.

## Окончательный вывод

### Технически

Да, проект с высокой вероятностью можно запустить на EdgeЦентр:

- Xray XHTTP — хороший кандидат для теста;
- Telegram Web Proxy/WebSocket — возможен после активации WebSocket и проверки heartbeat;
- прямой MTProto через CDN — нет.

### По доступности у мобильных операторов

Подтверждения «входит в белый список» нет и получить универсальную гарантию невозможно. Нужен отдельный контролируемый тест у каждого оператора. Наличие российского CDN и множества PoP повышает общую доступность, но ничего не говорит о разрешении конкретного пользовательского домена.

### Практическое решение

EdgeЦентр стоит взять для минимального теста только после письменного подтверждения допустимости сценария и параметров streaming/WebSocket. Не переносить production и не покупать большой пакет до проверки короткого HTTP, XHTTP и WebSocket на тестовом домене у нужных операторов.
