# План проверки GET-транспорта через Timeweb Cloud CDN

Дата: 2026-09-11

## Цель

Проверить существующие Xray XHTTP и Telegram Web Proxy AWG Manager через отдельный ресурс Timeweb Cloud CDN без изменения рабочих CDN-ресурсов и без зависимости от WebSocket Upgrade.

## Почему это может работать

Telegram Web Proxy проекта не обязан использовать нативный WebSocket CDN. Если клиент и сервер обмениваются данными через серию обычных HTTPS GET-запросов либо длительный GET-response, для CDN важны другие свойства:

- корректная передача query string и path;
- отсутствие кэширования динамического пути;
- поддержка длительного/потокового GET;
- допустимые таймауты обращения к origin;
- отсутствие буферизации ответа до полного завершения;
- передача нужных заголовков и корректный `Host`/SNI к origin.

Успешная работа через прежний CDN без generic WebSocket подтверждает, что Timeweb стоит проверять именно в GET-режиме.

## Безопасный стенд

1. Создать отдельный тестовый CDN-ресурс Timeweb, не заменяя существующий домен.
2. Указать текущий HTTPS origin либо отдельный тестовый hostname того же origin.
3. Назначить отдельные пути, например:
   - `/timeweb-test/xray/`;
   - `/timeweb-test/telegram/`.
4. Полностью отключить кэширование для этих путей либо установить bypass/no-cache правила.
5. Сохранить query string и исходный path без rewrite на первом тесте.
6. Добавить секретный origin header, если Timeweb позволяет, и проверять его на origin.
7. Не менять рабочие клиенты до прохождения readiness probe.

## Последовательность тестов

### 1. Базовый HTTP

- короткий GET через технический домен CDN;
- проверка status, body и заголовка маршрута;
- повтор с уникальным query parameter для обнаружения нежелательного кэша.

### 2. Длительный GET

- origin начинает ответ сразу и отправляет небольшие фрагменты с интервалом;
- измерить момент получения первого фрагмента клиентом;
- если клиент получает всё только после закрытия origin response, CDN буферизует поток и транспорт непригоден либо требует другой схемы polling.

### 3. Таймауты

- проверить idle intervals 15, 30, 60, 120 секунд;
- зафиксировать, когда CDN закрывает соединение;
- настроить heartbeat меньше фактического idle timeout.

### 4. Xray XHTTP GET

- создать временную клиентскую ссылку на Timeweb hostname/path;
- проверить handshake и минимальный трафик;
- проверить несколько последовательных запросов и переподключение;
- сравнить latency/throughput с прямым origin и прежним CDN.

### 5. Telegram Web Proxy

- создать отдельную тестовую ссылку/QR с Timeweb hostname и тестовым path;
- проверить подключение нативного Telegram-клиента;
- отправить и получить текст, фото и небольшой файл;
- проверить восстановление после смены сети и простоя;
- убедиться по origin/CDN logs, что запросы действительно проходят через Timeweb.

## Что логировать

- время, CDN hostname, client network;
- path без секретных query/token значений;
- HTTP status;
- time to first byte;
- длительность соединения;
- переданные байты;
- причина закрытия/timeout;
- origin route marker;
- успешность reconnect.

Секреты, client UUID и токены в отчёт и общий журнал не записывать.

## Критерии успеха

- CDN не возвращает кэшированный ответ между разными сессиями;
- первый фрагмент длительного GET приходит без ожидания закрытия origin;
- соединение либо polling стабильно переживает реальный сеанс Telegram;
- Xray/Telegram reconnect работает автоматически;
- origin подтверждает запросы именно от Timeweb CDN;
- технический и собственный CDN-домены работают одинаково после выпуска TLS.

## Критерии остановки

- CDN буферизует весь ответ и это нельзя отключить;
- минимальный timeout меньше допустимого heartbeat/polling цикла;
- CDN нормализует или удаляет обязательные query/header данные;
- правила услуги запрещают такой динамический HTTP-трафик;
- ресурс блокируется/приостанавливается провайдером.

## Изменения в AWG Manager после успешного стенда

Не делать отдельный код «под Timeweb». Использовать общий профиль CDN:

- display name;
- public hostname/port;
- origin hostname/port;
- path prefix;
- transport mode `GET streaming` или `GET polling`;
- cache bypass requirement;
- origin header name/value;
- heartbeat/request timeout;
- readiness probe и route marker.

Так тот же механизм останется применим к другим CDN с аналогичными HTTP-возможностями.

## Ограничения текущего этапа

- IPK не собирать.
- На роутеры ничего не устанавливать.
- Рабочие CDN-домены и конфигурации не изменять.
- Сначала проверить возможности отдельного Timeweb-ресурса, затем готовить точечную конфигурацию.
