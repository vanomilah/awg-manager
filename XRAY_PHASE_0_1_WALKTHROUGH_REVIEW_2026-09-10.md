## Итоговый вердикт

Phase 0 в основном реализована, однако Phase 1 пока нельзя принимать как безопасный фундамент полноценного управления Xray.

Пакет является промежуточной заготовкой. До интеграции нового конфигурационного ядра с хранением профилей, preview/apply и рабочим Xray необходимо устранить перечисленные ниже блокирующие недостатки.

## Блокирующие замечания

### 1. Компиляция outbounds фактически не реализована

Файл: `internal/xrayconfig/compiler.go`, функция `compileOutbound`.

Модель `Outbound` содержит поля:

- `Server`;
- `Port`;
- `UUID`;
- `Password`;
- `Transport`;
- `Security`;
- `Path` и `Host`;
- `TLS` и `Reality`.

Компилятор эти поля не преобразует в конфигурацию Xray. Для VLESS, VMess, Trojan, Shadowsocks, SOCKS и HTTP формируется пустой `settings`, если вызывающая сторона отдельно не передала готовый `RawSettings`.

Следствие: создать рабочий клиентский outbound через управляемую модель сейчас невозможно.

Требуется:

1. Реализовать компиляцию каждого заявленного протокола.
2. Формировать `settings` и `streamSettings` из типизированных полей.
3. Для ещё не поддержанных протоколов возвращать явную ошибку, а не пустую конфигурацию.
4. Добавить golden-тесты получаемого JSON для каждого поддерживаемого outbound.

### 2. Семантический diff пропускает существенные изменения

Файл: `internal/xrayconfig/diff.go`.

Сейчас не обнаруживаются:

- изменение существующего outbound;
- изменение правил маршрутизации;
- изменение `LogLevel` и `StatsEnabled`;
- изменение `Inbound.Listen`;
- изменение `Path` и `Host`;
- изменение TLS, Reality и sniffing;
- изменение `RawSettings`;
- изменение UUID, email, flow, level и remark существующего клиента.

При одном из таких изменений функция может вернуть:

```text
Конфигурация не изменилась
restart_required=false
```

Это опасно для будущего preview/apply: пользователь не увидит фактические изменения, а система может ошибочно решить, что применение или перезапуск не нужны.

Требуется:

1. Сравнивать все семантически значимые поля.
2. Добавить отдельные элементы diff для routing, log, stats, TLS, Reality и transport settings.
3. Определить стабильную идентичность сущностей, не полагаясь только на необязательный `Client.ID`.
4. Добавить тест, изменяющий по одному каждое поддерживаемое поле.
5. Добавить тесты, гарантирующие отсутствие секретов в описании diff.

### 3. `RedactConfig` не маскирует все возможные секреты

Файл: `internal/xrayconfig/redactor.go`.

Без обработки копируются:

- `ManagedConfig.Extra`;
- `Inbound.RawSettings`;
- `Outbound.RawSettings`.

Эти JSON-блоки могут содержать UUID, пароли, токены, приватные ключи и другие секреты. Поэтому утверждение walkthrough о полном безопасном маскировании конфигурации пока неверно.

Требуется:

1. Пропускать все raw/extra JSON через единый рекурсивный redactor.
2. Расширить перечень чувствительных имён: `privateKey`, `password`, `secret`, `token`, `uuid`, `id`, `authorization`, `psk`, `key` — с осторожной контекстной обработкой общих полей.
3. Не возвращать исходный raw slice из redacted-копии.
4. Добавить тесты секретов на разных уровнях вложенности и внутри массивов.

### 4. Ошибочный `RawSettings` молча игнорируется

Файл: `internal/xrayconfig/compiler.go`, функции `compileInbound` и `compileOutbound`.

Ошибка `json.Unmarshal` сейчас подавляется. После этого компилятор способен вернуть объект без корректного `settings`, хотя входные данные были повреждены.

Требуется возвращать ошибку с контекстом сущности и запрещать создание частично скомпилированной конфигурации.

Обязательные тесты:

- некорректный JSON inbound `RawSettings`;
- некорректный JSON outbound `RawSettings`;
- JSON корректен синтаксически, но верхний уровень не является объектом.

### 5. Проверка конфликтов портов неполная

Файл: `internal/xrayconfig/validator.go`.

Проверяется только точное совпадение строки `listen:port`. Например, не будет обнаружен потенциальный конфликт:

```text
0.0.0.0:443
192.168.90.1:443
```

Также необходимо определить поведение для:

- `[::]:port` и IPv4 на том же порту;
- пустого listen и его фактического значения;
- эквивалентных форм IPv6;
- wildcard относительно конкретного адреса.

Требуется вынести проверку пересечения bind-адресов в отдельную функцию и покрыть её табличными тестами.

## Существенные ограничения реализации

### 6. Заявление `lossless` применимо только к верхнему уровню `Document`

`Document.UnmarshalJSON` сохраняет неизвестные поля верхнего уровня. Однако:

- `Compiler.Compile` создаёт новый `Document`;
- `ManagedConfig.Extra` не переносится в создаваемый документ;
- неизвестные поля внутри inbounds/outbounds автоматически не сохраняются;
- VLESS inbound строится заново и не использует `RawSettings`.

Следовательно, реализация пока не обеспечивает lossless-редактирование произвольного существующего Xray-конфига.

До интеграции необходимо выбрать и зафиксировать контракт:

1. Либо AWG Manager полностью владеет конкретным профилем и явно предупреждает, какие поля поддерживаются.
2. Либо выполняется merge управляемых изменений в исходный `Document` с сохранением неизвестных секций и полей на каждом уровне.

Смешивать эти режимы без явной модели владения нельзя.

### 7. Валидатор не обеспечивает заявленную совместимость параметров

Проверяется список протоколов, путь и часть параметров Reality, но отсутствует полноценная матрица совместимости:

- протокол ↔ транспорт;
- транспорт ↔ security;
- обязательность TLS-сертификатов для серверного TLS;
- формат UUID;
- формат Reality private key и short ID;
- `OutboundTag` одновременно с `BalancerTag`;
- допустимые значения network, transport и security;
- пустой список активных клиентов для серверного VLESS.

Нужно определить capability matrix и использовать её одновременно в валидаторе, API и UI.

## Что можно принять сейчас

- безопасную нормализацию массивов capabilities;
- состояние ошибки и retry в мастерах как базовую защиту UI;
- каркас типов `Profile` и `ManagedConfig`;
- верхнеуровневый round-trip `Document` как отдельный примитив;
- начальный валидатор и redactor только как незавершённые внутренние компоненты;
- существующие unit-тесты как базовую стартовую точку.

## Что принимать пока нельзя

- готовность Phase 1 к production-интеграции;
- полноценное управление Xray;
- создание рабочих клиентских outbounds;
- безопасный preview/apply на основе текущего diff;
- полное маскирование секретов;
- lossless-редактирование произвольного Xray JSON;
- гарантию выявления конфликтов портов.

## Критерий завершения Phase 1

Phase 1 можно считать завершённой, когда:

- каждый заявленный типизированный объект компилируется в рабочий Xray JSON;
- любое поддерживаемое изменение отображается в diff;
- секреты не появляются ни в diff, ни в redacted API, ни в логах;
- повреждённые raw-поля приводят к явной ошибке до записи конфигурации;
- неизвестные данные сохраняются согласно документированному контракту владения;
- валидатор обнаруживает пересекающиеся bind-адреса и недопустимые сочетания параметров;
- соответствующие регрессионные тесты проходят.
