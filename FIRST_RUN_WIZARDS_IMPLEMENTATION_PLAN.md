# План реализации мастеров первого запуска Telegram Proxy и Xray

Статус: proposal  
Область: `Серверы → Telegram Proxy` и `Серверы → Xray VLESS`  
Цель: пользователь без знаний Xray, CDN, Fake-TLS и внутренних портов должен получить
рабочее подключение через пошаговый мастер, не открывая экспертные настройки.

## 1. Принципы продукта

1. Начинать с задачи пользователя, а не названия протокола.
2. Не просить данные, которые AWG Manager может определить или сгенерировать сам.
3. До применения показывать preflight и понятный план изменений.
4. Ничего не менять во время preflight/preview.
5. Применять конфигурацию транзакционно с rollback при неуспешной проверке.
6. Не показывать внутренние порты и transport-параметры в простом режиме.
7. Reveal, ссылки и QR открывать только явным действием и никогда не журналировать.
8. Существующие конфигурации не мигрировать и не перезаписывать автоматически.
9. Экспертный режим сохранить для полного ручного управления.
10. Мастер должен уметь продолжиться после перезагрузки страницы.

## 2. Целевой пользовательский поток

### 2.0. Универсальность конфигурации

Текущую рабочую конфигурацию пользователя сохранить как импортируемый частный шаблон
`CDN / GET`, но не использовать её как системные defaults. Ни один домен, IP, порт,
UUID, имя клиента, интерфейс или поставщик CDN не должен быть зашит в backend или UI.

Модель настройки должна разделять независимые оси:

- **серверный протокол**: Telegram MTProxy/Web Proxy либо Xray VLESS;
- **публичный вход**: прямой адрес, собственный reverse proxy или CDN;
- **транспорт**: поддерживаемые текущим ядром варианты, определяемые capabilities;
- **возможности CDN**: только GET, GET/POST, WebSocket, streaming/XHTTP либо другой
  обнаруженный набор возможностей — без привязки интерфейса к поставщику;
- **исходящий маршрут**: direct или любой созданный туннель/прокси AWG Manager;
- **настройка DNS**: универсальная инструкция либо необязательная автоматизация через
  подключаемый внешний adapter;
- **клиент**: Telegram, Happ, v2rayNG, sing-box, Mihomo, другой роутер;
- **уровень управления**: рекомендуемый automatic, ручной простой, экспертный.

Выбор одной оси не должен искусственно фиксировать остальные. Например, VLESS через CDN
не обязан использовать GET, порт 9008 или Mihomo `:1099`.

### 2.1. Telegram Proxy

Пустое состояние:

> Telegram Proxy ещё не настроен. Мастер проверит роутер и подготовит ссылку для
> подключения Telegram.

Шаги:

1. **Сценарий**
   - Через CDN — рекомендуется для сетей со специальными требованиями совместимости.
   - Прямой Telegram Proxy — проще, но зависит от доступности адреса.
   - CDN + резервный прямой вход.
2. **Автоматическая проверка**
   - архитектура и наличие бинарников;
   - доступность `telemt` и `tproxy-server`;
   - занятость портов;
   - доступность выбранного исходящего туннеля;
   - DNS и домен;
   - возможность запуска без изменения системы.
3. **Домен и CDN**
   - домен подключения;
   - профиль возможностей CDN;
   - исходящий туннель;
   - встроенная инструкция с готовыми Origin, WebSocket path и DNS value;
   - кнопка `Проверить снова`.
4. **Предпросмотр**
   - что будет установлено/запущено;
   - какие порты займутся;
   - какие файлы и init services изменятся;
   - выбранный egress;
   - предупреждения без технического мусора.
5. **Создание и проверка**
   - транзакционное применение;
   - readiness всех workers;
   - DNS/CDN probe;
   - rollback при критической ошибке.
6. **Подключение**
   - `Открыть в Telegram`;
   - `Показать QR`;
   - `Скопировать ссылку`;
   - краткая инструкция Android/iOS/Desktop;
   - `Проверить подключение`.

### 2.2. Xray

Пустое состояние:

> Xray ещё не настроен. Создайте защищённое подключение для телефона, компьютера или
> другого роутера.

Шаги:

1. **Устройство**
   - телефон;
   - компьютер;
   - другой роутер;
   - универсальная ссылка.
2. **Режим подключения**
   - автоматически выбрать — рекомендуется;
   - через CDN;
   - напрямую.
3. **Проверка окружения**
   - наличие и совместимость Xray;
   - свободные listener/dispatcher ports;
   - DNS/CDN reachability;
   - доступность egress;
   - конфликты с Mihomo, telemt и другими listeners.
4. **Домен/CDN или прямой адрес**
   - только необходимые для выбранного режима поля;
   - готовые значения для панели CDN;
   - автоматическая проверка.
5. **Клиент**
   - понятное имя, например `Телефон Ивана`;
   - UUID/path генерируются автоматически;
   - выбор egress простым названием туннеля.
6. **Предпросмотр и применение**
   - транзакционный apply;
   - config validation через Xray;
   - restart/readiness/rollback.
7. **Подключение**
   - QR и ссылка;
   - вкладки Happ, v2rayNG, sing-box/Mihomo и роутер;
   - проверка handshake/первого соединения.

## 3. Необходимая переработка backend

Мастер не должен собирать окончательный config в Svelte. Backend остаётся единственным
источником правил, defaults, валидации и применения.

### 3.1. Общий контракт мастера

Добавить пакет:

```text
internal/serverwizard/
  types.go
  preflight.go
  planner.go
  validation.go
```

Базовые DTO:

```go
type CheckState string // ok, warning, blocked, pending

type PreflightCheck struct {
    ID          string
    State       CheckState
    Title       string
    Summary     string
    Resolution  *Resolution
    Technical   string // только для раскрываемых подробностей
}

type ChangePlan struct {
    Kind        string
    Summary     []PlanItem
    Warnings    []PreflightCheck
    Fingerprint string
    ExpiresAt   time.Time
}
```

`Fingerprint` связывает preview и apply. Apply обязан отклонить устаревший план, если
состояние портов, config revision или выбранного туннеля изменилось.

### 3.2. API Telegram Wizard

Добавить защищённые endpoints:

```text
GET  /api/servers/tgwebproxy/wizard/capabilities
POST /api/servers/tgwebproxy/wizard/preflight
POST /api/servers/tgwebproxy/wizard/plan
POST /api/servers/tgwebproxy/wizard/apply
GET  /api/servers/tgwebproxy/wizard/jobs/{id}
POST /api/servers/tgwebproxy/wizard/jobs/{id}/cancel
```

Все POST используют существующий динамический CSRF-контур. `preflight` и `plan` строго
read-only. `apply` принимает fingerprint, создаёт job и использует существующую
tgwebproxy transaction/rollback инфраструктуру.

Preflight checks:

- binary/install state;
- ownership init scripts;
- port ownership, а не только `Dial`;
- chosen egress device and route;
- DNS A/AAAA/CNAME resolution;
- CDN origin reachability;
- TLS/SNI/domain consistency;
- required directories and permissions;
- recoveryRequired/operationInProgress.

### 3.3. API Xray Wizard

Добавить аналогичные endpoints:

```text
GET  /api/servers/xray/wizard/capabilities
POST /api/servers/xray/wizard/preflight
POST /api/servers/xray/wizard/plan
POST /api/servers/xray/wizard/apply
GET  /api/servers/xray/wizard/jobs/{id}
POST /api/servers/xray/wizard/jobs/{id}/cancel
```

До UI-мастера переработать `internal/xrayserver.Service`:

- убрать персональные домены, UUID и клиентов из defaults;
- новая установка: `Enabled=false`, пустой список Clients;
- не создавать клиента автоматически при пустом config;
- разделить `Validate`, `Render`, `Check`, `Apply`, `Rollback`;
- сохранять config атомарно с режимом 0600, потому что он содержит UUID/credentials;
- отказаться от глобальных `pidof xray`/`killall xray`; управлять только собственным PID,
  executable, starttime и точным config path;
- сначала запускать `xray run -test -config ...` либо поддерживаемый текущей версией
  эквивалент;
- при apply сохранять прежний config/process state и откатывать при failed readiness;
- сериализовать мутации и возвращать 409 при параллельной операции;
- добавить `Close()` и корректный shutdown;
- выдавать ссылки/UUID только через отдельный reveal/share endpoint с no-store и rate limit.

Это обязательный фундамент: текущий `UpdateConfig` сразу сохраняет и перезапускает Xray,
а defaults содержат конкретные домены и клиента, что неприемлемо для мастера новичка.

### 3.4. Каталог исходящих туннелей

Не привязывать мастер только к Mihomo. Переиспользовать единый каталог созданных
туннелей/выходов AWG Manager:

- стабильный ID;
- отображаемое имя;
- тип;
- interface/SOCKS endpoint;
- online/degraded state;
- поддержка TCP/UDP;
- владелец: AWG, WireGuard, subscription, Mihomo native и т.д.

UI показывает имя и состояние. Технический interface/port находится в раскрываемых
подробностях.

### 3.5. CDN capability profiles и transport adapters

Добавить расширяемые backend-контракты, основанные на возможностях CDN, а не на его
торговом названии:

```text
internal/serverwizard/cdn/
  profile.go
  custom.go
  probe.go
  presets.go

internal/serverwizard/transports/
  transport.go
  direct.go
  websocket.go
  xhttp.go
  telegram_get.go
```

CDN capability profile возвращает:

- разрешённые HTTP methods: GET-only, GET/POST или unrestricted;
- поддержку WebSocket/Upgrade;
- поддержку long-lived responses, streaming и режимов XHTTP;
- ограничения request body, response buffering и timeout;
- требуемые DNS records;
- Origin URL/port/path;
- поддержку WebSocket/HTTP methods/TLS;
- пошаговую инструкцию;
- read-only probe результата;
- опциональный automation adapter, если пользователь отдельно подключил внешний API.

Профиль выбирается одним из двух способов:

1. **Определить автоматически** — безопасная временная проверка обнаруживает поддержку
   GET/POST, WebSocket Upgrade, streaming, buffering и характерные timeout без изменения
   рабочей конфигурации.
2. **Указать возможности вручную** — пользователь отмечает известные ограничения CDN,
   если автоматическая проверка невозможна.

Географическое расположение CDN не участвует в transport logic. Любые CDN с одинаковым
набором возможностей получают один профиль и одинаковую конфигурацию. Регион может быть
только необязательной пользовательской меткой.

Transport adapter отвечает за совместимость server/client/core, defaults, validation и
рендеринг config fragment. UI получает JSON schema/field descriptors и не содержит
зашитой логики конкретного CDN или поставщика.

Первая версия обязана поддерживать:

- Telegram direct MTProxy;
- Telegram Web Proxy через совместимый CDN;
- профиль `CDN только с GET`;
- профиль `CDN с WebSocket`;
- профиль `CDN без ограничений методов`;
- Xray VLESS direct;
- Xray VLESS через совместимый CDN;
- XHTTP GET для GET-only CDN как проверенный transport preset;
- WebSocket/XHTTP streaming для CDN с соответствующими capabilities.

Интеграции с API конкретных сервисов можно добавлять позднее отдельными plugins без
изменения wizard shell и core API. Названия поставщиков не должны появляться в базовом
мастере.

### 3.6. Presets без персональных данных

Preset содержит только безопасные технические рекомендации:

```go
type ServerPreset struct {
    ID              string
    Kind            string
    CDNProfile      string
    Transport       string
    Recommended     bool
    DefaultPorts    []int
    CapabilityRules []string
}
```

Preset не содержит реальный домен, IP, UUID, secret, имя интерфейса или клиента.
Пользовательскую рабочую схему разрешается экспортировать как локальный private template,
который хранится отдельно, не входит в git/IPK и всегда маскирует credentials.

### Карточки Xray-core и Telemt в системных интеграциях

Карточка в разделе системных интеграций показывает только состояние установленного
компонента. Она не должна дублировать настройку соответствующего сервера.

Для `Xray-core` отображать:

- установлен ли исполняемый файл;
- версию ядра;
- состояние процесса и PID, если процесс запущен;
- кнопку `Скачать`, если ядро отсутствует;
- кнопку `Удалить`, если ядро установлено.

В этой карточке не должно быть описания транспорта, CDN, метода запросов, порта,
маршрутизации, клиентских ссылок или QR-кода. Создание и изменение сервера, выдача ссылки
и QR-кода выполняются только в `Серверы → Xray` по аналогии с разделением интерфейса
ядра и конфигурации у Sing-box и Mihomo.

Для `Telemt` действует та же модель:

- в системных интеграциях — только наличие исполняемого файла, версия, состояние процесса
  и PID;
- `Скачать`, если компонент отсутствует, и `Удалить`, если он установлен;
- без параметров Telegram Proxy, портов, доменов, ссылок и QR-кодов;
- вся настройка и управление Telegram Proxy находятся только в профильной карточке
  раздела `Серверы → Telegram Proxy`.

Обе карточки используют единый визуальный и поведенческий шаблон установленных ядер
Sing-box/Mihomo. Удаление требует подтверждения и не должно удалять пользовательскую
конфигурацию сервера без отдельного явно подтверждённого действия.

### Клиенты, статистика и создание туннеля

#### Xray

В интерфейсе роли Xray должны быть разделены явно:

- `Серверы → Xray` — Xray-core работает как **сервер**: принимает подключения созданных
  здесь VLESS-клиентов и направляет их трафик в выбранный выход;
- `Прокси → Туннели` — Xray-core может работать как **клиентское ядро** для импортированного
  VLESS-профиля и предоставляет этот outbound маршрутизации AWG Manager;
- установленный бинарник Xray-core общий, но серверная и клиентская конфигурации,
  процессы, порты, журналы и состояния разделены;
- карточка интеграции Xray-core показывает только наличие и версию бинарника и не создаёт
  впечатление, что сервер или клиент уже настроен.

Заголовок и статус всегда называют роль: `Xray-сервер`, `Xray-клиентский туннель` или
`Ядро Xray-core`. Нельзя использовать одно название `Xray` для трёх разных состояний.

Клиент Xray — это отдельная учётная запись входящего VLESS-сервера, а не готовый
туннель на текущем роутере. Для каждого клиента хранится собственный UUID, отображаемое
имя, состояние и стабильный внутренний идентификатор статистики.

Карточка клиента должна показывать:

- включён/отключён;
- общий входящий и исходящий трафик;
- время последней активности, только если оно подтверждено изменением счётчиков;
- число активных соединений, только если эту метрику предоставляет установленная версия
  Xray;
- действия `Подключить`, `Изменить`, `Отключить` и `Удалить`.

Backend включает локальный Stats API Xray и получает per-user uplink/downlink по
стабильному идентификатору клиента. API статистики слушает только loopback и не
публикуется в LAN/WAN. После перезапуска процесса AWG Manager корректно продолжает
накопительные значения либо явно показывает статистику текущего запуска. Запрещено
подменять отсутствующие per-user данные общими счётчиками интерфейса.

Карточка Xray-сервера содержит сводную статистику:

- активные и отключённые клиенты;
- клиенты с трафиком за последние 24 часа;
- текущая суммарная скорость приёма и передачи;
- суммарный трафик за сутки, 7 дней и всё время;
- таблица клиентов с сортировкой по трафику и последней активности;
- график суммарного трафика и раскрываемый график выбранного клиента;
- состояние Stats API и время последнего успешного обновления.

AWG Manager периодически снимает дельты счётчиков Xray и хранит только агрегаты временных
интервалов, а не содержимое соединений. Для роутера с ограниченной памятью использовать
кольцевое хранилище: подробные точки за 24 часа, часовые агрегаты за 7 дней и суточные
агрегаты за выбранный срок хранения. Должны быть действия `Сбросить статистику` и
`Экспорт CSV`, не затрагивающие UUID и конфигурацию клиентов.

Кнопка `Подключить` открывает единый результат мастера с вариантами использования:

1. `Телефон или компьютер` — VLESS URL, QR-код и конфигурация для совместимого клиента.
2. `Другой роутер с AWG Manager` — переносимый профиль без серверных приватных данных.
   На другом роутере профиль импортируется в `Прокси → Добавить туннель`, пользователь
   выбирает только совместимое с транспортом ядро, после чего создаётся outbound и, при
   необходимости, локальный интерфейс туннеля для NDMS, политик доступа и других
   маршрутизаторов. Несовместимые ядра не предлагаются.
3. `Ручная настройка` — параметры подключения и конфигурационные фрагменты поддерживаемых
   форматов.

Импортированный Xray-профиль можно использовать:

- как выход отдельной политики или устройства;
- как участника proxy-группы;
- как маршрут для выбранных доменов и сетей;
- как системный туннель, доступный другим подсистемам AWG Manager через локальный
  туннельный интерфейс.

Создавать такой outbound автоматически на том же роутере, где работает соответствующий
Xray-сервер, по умолчанию нельзя: это обычно образует бессмысленный локальный цикл.
Мастер должен распознавать совпадение сервера и предупреждать пользователя.

Для текущего XHTTP-профиля импорт разрешается только после проверки реальной поддержки
в выбранном клиентском ядре и успешной валидации сгенерированной конфигурации. Наличие
поля `xhttp` в формируемом JSON/YAML не считается доказательством совместимости. Если
Mihomo или Sing-box текущей версии не поддерживает профиль, мастер предлагает Xray-core
как клиентское ядро либо экспорт для внешнего совместимого приложения.

Отдельно от клиентского туннеля настраивается маршрут выхода самого Xray-сервера:
`Прямой выход` отправляет принятый клиентский трафик через обычный интернет роутера, а
`Через существующий прокси/туннель` передаёт его в выбранный локальный SOCKS endpoint.
В простом режиме пользователь выбирает существующий туннель по имени; номер локального
порта определяется AWG Manager автоматически и не вводится вручную.

#### Полноценный клиентский режим Xray-core

Установленный Xray-core должен использоваться не только сервером. В
`Прокси → Туннели → Добавить` добавить выбор клиентского ядра `Xray-core` рядом с
Mihomo и Sing-box. Этот сценарий принимает сторонний профиль и создаёт самостоятельный
клиентский туннель AWG Manager.

Поддерживаемые способы добавления:

- URI поддерживаемого протокола;
- подписка с одним или несколькими профилями;
- клиентский JSON Xray;
- ручная форма простого режима;
- переносимый профиль, экспортированный другим AWG Manager.

Список протоколов и транспортов нельзя задавать статически. Backend определяет версию и
capabilities установленного Xray-core, разбирает профиль в промежуточную модель, затем
рендерит и обязательно проверяет итоговую конфигурацию командой самого ядра. UI показывает
только реально поддерживаемые текущей версией комбинации.

Серверный и клиентский режим используют один бинарник, но полностью раздельные runtime:

- отдельные конфигурации и PID/state-файлы;
- отдельные локальные API и журналы;
- независимые start/stop/reload/recovery;
- отдельные диапазоны автоматически выделяемых портов;
- отсутствие общих mutable-файлов кроме read-only бинарника;
- запрет остановки клиентского runtime при изменении Xray-сервера и наоборот.

Для экономии памяти клиентские туннели по умолчанию работают в одном управляемом
`Xray client runtime` с несколькими outbounds. Для каждого туннеля AWG Manager создаёт
отдельный loopback SOCKS-inbound и устойчивый внутренний tag. Изменения применяются
атомарной генерацией, проверкой и reload общего клиентского runtime. Если профиль требует
несовместимых глобальных параметров, backend может вынести его в отдельный изолированный
процесс и явно показать это в диагностике.

Созданный Xray-клиент регистрируется в общем каталоге прокси-туннелей наравне с
Mihomo/Sing-box и получает:

- стабильный ID, имя, тип `xray-client` и ссылку на исходный профиль;
- локальный SOCKS endpoint для приложений и цепочек;
- при включённой системной интеграции — адаптер в управляемый `opkgtunN` для NDMS и
  подсистем, которым нужен сетевой интерфейс;
- состояние, задержку, статистику, журнал и диагностику;
- проверки соединения и внешнего IP через конкретный outbound;
- защиту от удаления, пока на туннель ссылаются политики, правила или proxy-группы.

Варианты использования в UI:

- назначить туннель устройству или политике доступа;
- выбрать его выходом правила маршрутизации;
- добавить в selector, fallback, url-test или load-balance группу, если семантика группы
  поддерживает внешний локальный outbound;
- выбрать маршрутом загрузки подписок, запросов ИИ и других сервисов AWG Manager;
- предоставить локальному приложению Entware SOCKS endpoint;
- опубликовать его в NDMS как управляемый туннельный интерфейс.

Импорт обязан обнаруживать локальный цикл: профиль, ведущий на Xray-сервер этого же
роутера, нельзя включать без отдельного экспертного подтверждения. Секреты и полные URI
хранятся с правами `0600`, маскируются в API/логах и не включаются в обычный экспорт
диагностики.

#### Telegram Proxy / Telemt

Для Telegram Proxy применяется такой же принцип карточек клиентов, но набор метрик
зависит от возможностей установленной версии Telemt:

- отдельное имя и отдельный secret для каждого нового клиента;
- включение, отзыв и безопасная ротация доступа конкретного клиента;
- индивидуальные ссылки и QR-коды;
- per-client трафик, последняя активность и соединения — только при наличии надёжного
  источника этих данных в Telemt;
- если Telemt предоставляет только общие показатели, UI показывает их на уровне сервера
  с явной пометкой `Общая статистика`, без ложного распределения по клиентам.

Сводная карточка Telegram Proxy разделяет два независимых канала подключения:

- `Web Proxy через CDN`;
- `MTProto Direct`.

Для каждого канала отдельно показываются доступные метрики: состояние listener/worker,
активные подключения, текущая скорость, принятый и переданный трафик, успешные подключения
за период, ошибки подключения и время последней активности. Над ними показывается общий
итог Telegram Proxy без двойного учёта одного и того же трафика.

Таблица клиентов содержит отдельные колонки `Web Proxy` и `MTProto Direct`, чтобы было
видно, каким способом пользовался клиент. Для каждой колонки отображаются трафик,
последняя активность и текущие соединения, если источник метрик позволяет надёжно связать
событие с конкретным secret. Один логический клиент может иметь два отдельных credentials:
один для Web Proxy и один для MTProto Direct. Отзыв одного способа подключения не должен
автоматически отзывать второй.

Backend нормализует метрики разных процессов в единую модель:
`channel`, `client_id`, `connections_active`, `connections_total`, `uplink_bytes`,
`downlink_bytes`, `last_seen`, `errors_total` и `available_fields`. UI обязан учитывать
`available_fields` и не показывать нулём показатель, который на самом деле недоступен.
Хранение истории и сроки агрегации совпадают со статистикой Xray-сервера.

Перед реализацией статистики backend выполняет capability detection для конкретного
бинарника Telemt и Web Proxy worker. Допустимые источники — нативный API/metrics endpoint,
счётчики собственного worker или структурированный журнал с идентификатором пользователя.
Подсчёт клиентов только по сокетам или общему трафику процесса не считается per-client
статистикой.

Telegram Proxy предназначен для подключения Telegram-клиента по выданной ссылке или
QR-коду. Он не должен отображаться как универсальный IP-туннель и не добавляется в
маршрутизацию NDMS, Mihomo или Sing-box, если используемый протокол не предоставляет
полноценный сетевой outbound.

### Состояния карточки сервера

Карточки `TelegramWebProxyCard.svelte` и `XrayServerCard.svelte` должны различать:

- `not_configured` — большая CTA `Настроить`;
- `draft` — `Продолжить настройку`;
- `applying` — progress с безопасным восстановлением после reload;
- `running` — текущая рабочая карточка;
- `degraded` — причина и `Исправить через мастер`;
- `recovery_required` — отдельный аварийный экран, без обычного apply.

Не определять `not_configured` только по `running=false`. Backend должен возвращать
`configured`/`revision` явно.

### Простой и экспертный режим

- мастер и рабочая карточка — простой режим;
- текущие settings modals становятся экспертным режимом;
- переход в expert показывает предупреждение, но не блокирует пользователя;
- поля имеют справку `Что это?` и кнопку возврата к рекомендуемым значениям;
- экспертные изменения увеличивают config revision и инвалидируют открытый wizard plan.

### Сохранение черновика

В localStorage хранить только несекретные UI-ответы: шаг, scenario, device kind и display
names. Домены допустимы. Никогда не хранить UUID, secret, share links, CSRF tokens и QR.
Backend draft нужен только если настройку требуется продолжать между устройствами.

## 5. UX диагностики и исправлений

Каждая проблема preflight должна содержать:

- короткий заголовок: `Порт 8443 занят`;
- понятное объяснение: `Его использует другой сервис`;
- безопасное действие: `Выбрать свободный порт`;
- раскрываемые детали: PID, process, socket, команда проверки;
- статус повторной проверки.

Типы resolution:

- `auto_safe` — можно применить одной кнопкой;
- `manual_external` — DNS/CDN действие вне роутера;
- `choice_required` — несколько безопасных вариантов;
- `blocked` — продолжение невозможно.

Мастер не должен автоматически останавливать чужой процесс, менять DNS/CDN или удалять
чужой config.

## 6. Безопасность

- Все mutation endpoints: auth + CSRF + Same-Origin + method enforcement.
- Preflight не раскрывает секреты, содержимое конфигов и environment.
- Apply требует plan fingerprint и config revision.
- Share/reveal: `Cache-Control: no-store`, rate limit, audit event без payload.
- QR очищается из памяти при закрытии modal/unmount.
- Backend и frontend logs маскируют UUID, secret, URL query и subscription data.
- Ротация не выполняется автоматически при повторном открытии мастера.
- Любое удаление/перезапись существующего сервера требует отдельного подтверждения и
  backup.
- Импорт/экспорт wizard draft не включает credentials.

### 6.1. Нейтральная терминология

Все пользовательские тексты Telegram Proxy и Xray должны описывать только назначение и
технические свойства функции. В базовом UI, API messages, generated link labels,
документации, presets и screenshots запрещены:

- названия конкретных CDN и операторов;
- геополитические и региональные характеристики;
- утверждения о противодействии внешним ограничениям или системам анализа трафика;
- названия инфраструктурных механизмов контроля доступа, не требуемые для настройки;
- юридические оценки и предположения о допустимости использования;
- маркетинговые обещания скрытия, неотслеживаемости или гарантированной доступности.

Допустимая терминология:

- `подключение через CDN`;
- `прямое подключение`;
- `совместимость с GET-only CDN`;
- `поддержка WebSocket/streaming`;
- `публичный адрес origin не передаётся клиенту`;
- `доступность зависит от выбранной сети и конфигурации CDN`.

Добавить автоматический lint пользовательских строк и документации по словарю проекта.
Исключения допустимы только в developer-only tests/research notes и не должны попадать в
сборку, UI или публичную документацию.

## 7. Порядок реализации

### Этап 0. Зафиксировать UX и контракты

- wireframes обоих мастеров;
- таблица полей simple/expert;
- DTO и OpenAPI без реализации;
- тексты ошибок и resolution actions;
- acceptance scenarios.

Результат: согласованный UI flow и API contract.

### Этап 1. Xray safety foundation

- безопасные defaults и миграция существующего config;
- atomic storage 0600;
- process identity вместо killall/pidof;
- render/check/apply/rollback;
- mutation lock и recovery state;
- unit/integration tests.

Результат: Xray можно безопасно конфигурировать программно.

### Этап 2. Общий preflight/planner

- `internal/serverwizard`;
- catalog egress adapters;
- port/DNS/domain/CDN checks;
- plan fingerprint/revision;
- job status и events.

Результат: оба мастера получают единый диагностический язык.

### Этап 3. Telegram Proxy Wizard MVP

- empty state;
- сценарии CDN/direct/both;
- preflight и manual CDN guide;
- preview/apply/progress;
- connection result;
- сохранение несекретного draft.

Результат: новый пользователь создаёт Telegram Proxy без экспертной формы.

### Этап 4. Xray Wizard MVP

- device-first flow;
- automatic/CDN/direct selection;
- client creation;
- preview/apply/verify;
- client-specific connection instructions.

Результат: новый пользователь создаёт первый Xray client и подключает устройство.

### Этап 5. Xray client runtime

- импорт URI, подписки, JSON и переносимого профиля;
- capability detection и config validation установленным Xray-core;
- отдельный от сервера client runtime;
- общий каталог туннелей, loopback SOCKS и опциональный `opkgtunN` adapter;
- использование в политиках, правилах, proxy-группах и сервисных запросах;
- статистика, тест соединения, внешний IP, журнал и безопасное удаление;
- защита от циклов и ссылочной целостности;
- unit/integration tests и проверка восстановления после reload/reboot.

Результат: сторонний совместимый профиль можно импортировать и использовать через
Xray-core как полноценный клиентский туннель AWG Manager.

### Этап 6. Repair flows

- `Исправить через мастер` для degraded карточек;
- resume jobs after reload;
- rollback UI;
- DNS/CDN recheck;
- интеграция с ИИ-помощником через те же typed tools, без shell bypass.

### Этап 7. Polish и документация

- responsive/mobile;
- keyboard/focus/accessibility;
- onboarding help;
- telemetry только локальная и без секретов;
- screenshots без QR/credentials;
- обновление OpenAPI и пользовательской документации.

## 8. Тестирование

### Backend

- preflight строго read-only;
- occupied port и PID ownership;
- missing/down egress;
- DNS mismatch/timeout/NXDOMAIN;
- stale fingerprint/revision -> 409;
- apply success;
- config check failure -> no mutation;
- readiness failure -> rollback;
- crash recovery на каждой фазе;
- concurrent apply -> 409;
- existing config preserved;
- no secret serialization/logging;
- Xray process identity/PID reuse;
- CSRF/method/session negative tests.

### Frontend

- переходы и возврат между шагами;
- refresh/resume draft и active job;
- blocked/warning/resolution states;
- simple/expert switch;
- отсутствие secrets в localStorage;
- QR cleanup on close;
- API errors не оставляют вечный spinner;
- mobile layout;
- a11y focus trap и keyboard navigation.

### E2E на тестовом роутере

1. Чистая установка без конфигов.
2. Создание Telegram CDN.
3. Создание Telegram direct.
4. Занятый порт и безопасный автоматический выбор.
5. Ошибочная DNS-запись и повторная проверка.
6. Создание Xray client для Android.
7. Неуспешный Xray config check и rollback.
8. Потеря egress во время apply.
9. Refresh браузера во время job.
10. Проверка существующей ручной конфигурации без изменения.
11. Upgrade с текущей 2.17.36 без автоматического запуска мастера.
12. Проверка, что screenshots/logs/export не содержат credentials.

## 9. Acceptance criteria

### Telegram Proxy

- новичок завершает настройку максимум за 5 пользовательских решений;
- технические поля не обязательны в recommended flow;
- DNS/CDN инструкция содержит готовые копируемые значения;
- failed apply возвращает прежний рабочий config и processes;
- успешный результат выдаёт рабочую ссылку только по явному reveal;
- после перезагрузки UI корректно продолжает job/draft.

### Xray

- новая установка не содержит чужих доменов, UUID или клиентов;
- новичок создаёт клиента, выбрав устройство, режим и имя;
- Xray config проверяется до замены рабочего config;
- AWG Manager не останавливает посторонний процесс Xray;
- failed readiness восстанавливает прежний config/process;
- ссылки подходят выбранному клиенту и не попадают в persistent browser storage.

### Общие

- существующие пользователи не теряют текущие конфигурации;
- simple UI не использует термины Origin/backend/XMUX без пояснения;
- все операции имеют однозначный статус и дальнейшее действие;
- нет force install, shell-команд из UI и скрытых destructive actions;
- frontend check/build, Go tests, OpenAPI drift и E2E проходят.
