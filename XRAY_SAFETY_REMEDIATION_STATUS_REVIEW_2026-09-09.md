## Вердикт

**Walkthrough исправлен как статусный документ, но ремедиация в коде ещё не выполнена.**

Новая редакция больше не утверждает, что этап завершён, честно запрещает установку на роутер и правильно перечисляет все семь замечаний: три P0 и четыре P1. В таком виде документ можно использовать как список работ.

Однако это пока не walkthrough выполненной реализации, а план/журнал предстоящей ремедиации. Проверка исходников показывает, что найденные ранее дефекты остаются на месте.

## Проверка заявленных пунктов по коду

### 1. Координатор в control plane — не исправлено

- `cmd/awg-manager/wiring_server.go:128`: координатор по-прежнему создаётся локальной переменной `ingressCoord` и после `StartupRecovery()` теряется.
- `internal/server/server_routes.go:499`: `XrayServerHandler` по-прежнему получает только `xrayServerService`.
- Мутации API всё ещё напрямую вызывают методы сервиса, минуя coordinator.

### 2. Единый transaction ID — не исправлено

- Интерфейс всё ещё имеет сигнатуру `PrepareCandidate(candidate)`.
- `xrayserver.PrepareCandidate()` самостоятельно генерирует `tx-*`.
- `StartupRecovery()` всё ещё вызывает `RollbackPrepared(j.TransactionID)` с coordinator ID `ing-*`.
- Поля `ComponentTransactionIDs` в журнале нет.

### 3. Отложенный finalize — не исправлено

- Метода `FinalizePrepared` нет.
- `CommitPrepared()` всё ещё удаляет snapshot через `os.RemoveAll(txPath)` в `internal/xrayserver/transaction.go:255`.

### 4. Checksum и строгий recovery — не исправлено

- В `TransactionJournal` отсутствуют поля `Version` и `Checksum`.
- Ошибки component rollback по-прежнему игнорируются, после чего журнал может быть архивирован как recovered.

### 5. Process identity — не исправлено

- Типа `PIDRecord` нет.
- В PID-файл всё ещё записывается только число.
- Контроль start time и binary fingerprint отсутствует.

### 6. Безопасная миграция — не исправлено

- Проверка symlink target всё ещё использует `strings.HasPrefix` в `internal/xrayserver/migration.go:123`, а не `filepath.Rel`.
- Ошибки записи migration marker и runtime decision всё ещё подавляются в `migration.go:294` и `migration.go:303`.

### 7. Очистка старого `XrayHandler` — не исправлено

- Сохраняется вызов `pidof xray` в `internal/api/xray_handler.go:269-270`.
- Сохраняется hardcoded адрес `95.79.35.140` в `xray_handler.go:126`.
- Старые пути и assumptions обработчика ещё присутствуют.

## Оценка самого документа

Что теперь сделано правильно:

- статус не преувеличивает готовность;
- запрет деплоя сформулирован явно;
- все замечания предыдущего аудита перенесены без потерь;
- предлагаемые способы исправления технически соответствуют аудиту;
- количество замечаний теперь указано правильно: **3 P0 + 4 P1**.

Что следует изменить после реализации:

- не называть документ финальным walkthrough до появления diff и результатов проверок;
- для каждого пункта добавить конкретные изменённые файлы, тесты и фактический результат;
- отдельно привести новые интеграционные crash-point сценарии, а не только повтор старого набора тестов;
- после завершения заменить warning «выполняется устранение» на итоговый статус только при закрытии всех семи пунктов.

## Итог

Документ можно передать агенту и продолжать по нему работу. **Повторный деплой пока запрещён.** Следующее ревью нужно выполнять после реальных изменений в исходниках; критерием готовности должно быть не обновление текста walkthrough, а закрытие перечисленных кодовых признаков и прохождение новых интеграционных тестов.
