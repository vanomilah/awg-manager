# Ревью `implementation_plan.md` после аудита Telegram Web Proxy

Дата: 2026-09-09

## Вердикт

План закрывает почти все замечания предыдущего аудита и может служить основой для
третьей ремедиации, но запускать его без корректировок не следует. Требуются четыре
обязательные правки: штатная установка без force-флагов, корректная команда API-тестов,
безопасное сохранение manifest при частичном восстановлении и защита файлов ключей от
symlink/неатомарной записи.

## Что в плане сделано правильно

- предусмотрена ротация раскрытого Telegram-секрета и отзыв legacy-секрета;
- сырые секрет и CSRF-токен удаляются из walkthrough и live test output;
- `SessionStore == nil` переводится в fail-closed поведение;
- политика Origin/Referer для `/csrf` явно фиксируется и покрывается тестами;
- `GetCSRFSecret()` должен возвращать копию;
- manifest записывается только после успешного backup;
- SHA-256 должен проверяться перед восстановлением;
- `--force-overwrite`, `--force-reinstall` и `--cleanup` исключены;
- предусмотрены backend, frontend и live-проверки.

## Обязательные изменения перед запуском

### P1 — устанавливать обновление вообще без force-флагов

План повышает версию с `2.17.35` до `2.17.36`, поэтому `--force-downgrade` не нужен.
Правильная целевая команда:

```sh
opkg install /opt/tmp/awg-manager_2.17.36_aarch64-3.10-kn.ipk
```

Если обычная установка сообщает конфликт или считает пакет downgrade, нужно остановиться
и выяснить владельца файлов/правила сравнения версий, а не обходить проверку force-флагом.

### P1 — команда API-тестов в плане не является воспроизводимой

Команда с перечислением двух файлов и литералом `...` непригодна для запуска. Использовать
пакетный тест в Linux/WSL либо на ARM64:

```sh
go test -v ./internal/api -run 'TgWebProxy|CSRF'
```

После него запустить минимум:

```sh
go test ./internal/tgwebproxy/... ./internal/api
```

Если пакет `internal/api` зависит от Linux-only реализации, это нужно выполнять через WSL
или ARM64-среду, а не объявлять Windows-ошибку результатом тестирования.

### P1 — manifest нельзя удалять целиком после пропущенной записи

Формулировка «удалять manifest entry только после успешного восстановления» правильная,
но текущий `prerm` в конце безусловно удаляет весь manifest. Реализация должна:

1. создать новый временный manifest;
2. переносить в него записи, которые не удалось проверить или восстановить;
3. атомарно заменить исходный manifest, если остались записи;
4. удалить manifest только когда успешно обработаны все записи.

При несовпадении SHA резервную копию и запись manifest необходимо сохранить.

### P1 — добавить безопасную работу с `token.key` и `csrf.key`

Текущий код использует `os.Stat`, `os.ReadFile` и `os.WriteFile`, которые следуют symlink.
Для сервиса, работающего от root, это опасно. В план следует включить общий helper для
защищённых ключевых файлов:

- проверить путь через `os.Lstat` и отклонить symlink/необычный тип файла;
- создавать новый файл с `O_CREATE|O_EXCL` и режимом `0600`;
- для замены писать временный файл в том же каталоге, делать `fsync`, затем `rename`;
- после открытия проверить regular file, размер и права;
- каталог `/opt/etc/awg-manager/tproxy` должен оставаться `0700`;
- добавить тесты на symlink, неправильный тип, короткий файл и ошибку записи.

Ручное удаление `csrf.key` на роутере допускается только после остановки AWG Manager и
проверки `lstat`, что это обычный файл по точному ожидаемому пути. Предпочтительнее сделать
контролируемую серверную операцию ротации ключа.

## Уточнения к P0 и live-операциям

- Простого редактирования walkthrough недостаточно, если секрет уже попал в историю Git,
  чат, логи или загруженные артефакты. Основной способ обезвреживания — ротация и отзыв.
- После ротации проверить старую ссылку отрицательным тестом: она больше не должна
  подключаться.
- CSRF-токен привязан к сессии. После ротации `csrf.key` нужно завершить старую admin
  сессию и войти снова.
- Утверждение, что порт `:2222` «останется intact», неточно: при рестарте AWG Manager будет
  короткий перерыв. Остальные процессы нельзя перезапускать без необходимости.
- Перед любыми изменениями роутера требуется отдельное подтверждение пользователя и
  резервная копия соответствующих конфигов. Кодовые исправления и тесты можно выполнить
  раньше, не трогая роутер.

## Дополнительные тесты

Добавить к уже указанным в плане:

1. `/csrf` с валидным Origin, валидной сессией и пустым SessionStore;
2. `/csrf` с несовпадающим Host/Origin, включая порт;
3. mutating endpoint с валидным токеном, но отсутствующими Origin/Referer;
4. параллельные запросы `/csrf` и запуск с race detector в Linux;
5. symlink-тесты для обоих key-файлов;
6. upgrade/remove с частично повреждённым `.bak` и несколькими manifest entries;
7. обычный `opkg install` без force-флагов;
8. поиск утечек перед завершением:

```sh
git grep -nE 'Revealed secret|CSRF response|csrf_token'
```

Результаты поиска нужно проверять вручную: имена JSON-полей допустимы, реальные значения —
нет. Не печатать секреты в терминал/отчёт при этой проверке.

## Рекомендуемый порядок выполнения

1. Исправить API, key-file helper, `preinst` и `prerm`.
2. Добавить и выполнить unit/integration tests в Linux-совместимой среде.
3. Очистить walkthrough и тестовые скрипты от значений.
4. Собрать IPK и проверить его состав/владельцев локально.
5. Получить подтверждение на операции с роутером.
6. Сделать backup, ротировать секреты, установить IPK обычной командой.
7. Выполнить live smoke/security tests без вывода секретов.
8. Зафиксировать точные команды, exit codes и остаточные ограничения в walkthrough.

После внесения этих изменений план можно запускать в работу.
