## Найденные проблемы

### P1 — `preinst` не исправлен

В `entware/control/preinst` команда копирования всё ещё заканчивается `|| true`, после
чего запись безусловно добавляется в manifest:

```sh
cp -p "$target" "$bak" ... || cp "$target" "$bak" ... || true
echo "$script $sha" >> "$MANIFEST"
```

При неудачном backup manifest сообщает о резервной копии, которой нет. Это прямо
противоречит утверждённому плану.

Нужно добавлять запись только внутри успешной ветки `if cp ...; then`, а при ошибке
печатать предупреждение и не создавать запись.

### P1 — walkthrough выдаёт старый deploy за результат новой ремедиации

Документ указывает пакет `2.17.35` и команду:

```text
opkg install --force-downgrade --force-overwrite ...2.17.35...
```

При этом фактический `VERSION` уже равен `2.17.36`, а согласованный план требует обычный
`opkg install` без force-флагов. Разделы deploy/live/UI относятся к предыдущему прогону и
не подтверждают текущий код.

Нужно удалить старые результаты либо явно пометить их как historical, затем после
разрешения пользователя провести отдельную проверку 2.17.36 штатной установкой.

### P1 — key-file helper всё ещё имеет TOCTOU при чтении существующего ключа

Код делает `os.Lstat(keyPath)`, а затем отдельно `os.Open(keyPath)`. Между этими операциями
путь может быть заменён на symlink, после чего `os.Open` последует ему. Для процесса root
это не является полной защитой от symlink attack.

На Linux следует открывать файл с `O_NOFOLLOW`, затем проверять `f.Stat()` и читать уже из
проверенного descriptor. Альтернатива — platform helper с Linux-реализацией через
`golang.org/x/sys/unix` и безопасным stub для других платформ.

Также временный файл создаётся с `O_TRUNC`, а не `O_EXCL`. Имя достаточно трудно угадать,
но требование утверждённого плана было строже. Использовать случайное имя через
`os.CreateTemp(dir, ...)`, сразу chmod 0600 и проверенный descriptor.

### P1 — повреждённый ключ переименовывается до успешной генерации нового

При неверном размере старый ключ сначала переносится в `.corrupt.*`, и только затем
вызывается RNG и создаётся новый файл. При отказе entropy/write сервис остаётся без
канонического key file. Безопаснее сначала сгенерировать и синхронизировать новый temp
file, затем атомарно сохранить старый и заменить ключ с корректным rollback при ошибке.

### P2 — описание пути `csrf.key` в walkthrough неверно

Документ указывает `/opt/etc/awg-manager/csrf.key`, фактический код использует
`/opt/etc/awg-manager/tproxy/csrf.key`. Операционная инструкция с неправильным путём
может привести к ложной ротации неиспользуемого файла.

### P2 — новый набор тестов не отражён в walkthrough

В коде появились тесты symlink/non-regular/corrupt key и immutable slice, но walkthrough
всё ещё приводит старый список из 22 тестов. Нет результатов:

- новых тестов `loadOrCreateKeyFile`;
- nil SessionStore;
- missing/mismatched Origin/Referer;
- manifest restore с частичным отказом;
- реального browser smoke-test после строгого GET `/csrf`;
- отрицательной проверки старой Telegram-ссылки после ротации.

### P2 — leak check нельзя считать полностью подтверждённым

Полные значения в самом walkthrough теперь затёрты, что правильно. Но документ не
показывает проверку внешних/untracked artifacts и истории. Название «ZERO LEAKS» означает
только отсутствие секрета в приведённом выводе, а не во всех местах, куда он уже мог
попасть. Безопасность достигается ротацией, которая в этом новом прогоне не подтверждена.
