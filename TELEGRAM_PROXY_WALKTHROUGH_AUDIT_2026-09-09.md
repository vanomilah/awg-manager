## Вердикт

Основная ремедиация реализована существенно лучше предыдущей версии, а целевой пакет
`internal/tgwebproxy` проходит тесты. Однако принимать результат как полностью готовый
пока нельзя: в отчёте опубликован действующий секрет Telegram-прокси, а CSRF-контур
содержит два fail-open/нестрогих участка. Перед дальнейшим распространением сборки
нужна короткая третья ремедиация.

## Найденные проблемы

### P0 — в walkthrough опубликован действующий секрет

В разделе live-проверки записано полное значение, возвращённое `POST /reveal`, а также
действующий CSRF-токен. Маскированного значения было достаточно. Файл нельзя публиковать,
коммитить или передавать третьим лицам в текущем виде.

Что сделать:

1. Немедленно заменить основной секрет Telegram-прокси и отозвать legacy-секрет.
2. Завершить текущую административную сессию; безопаснее также пересоздать `csrf.key` при
   остановленном AWG Manager и затем снова войти.
3. Удалить полные значения из `walkthrough.md`, артефактов тестов, истории агента и логов.
4. Изменить live-тест: печатать только длину и маску, никогда не тело ответа `/reveal`.

Значения секретов намеренно не повторяются в этом аудите.

### P1 — проверка сессии CSRF работает fail-open при `sessions == nil`

`internal/api/tg_webproxy.go` проверяет сессию только внутри условия
`if h.sessions != nil`. При ошибке wiring-а или тестовой/альтернативной сборке любой
непустой cookie становится достаточным для выдачи CSRF-токена и проверки HMAC.
Для security-sensitive handler отсутствие SessionStore должно давать 503/false.

Рекомендуемая правка:

- в `GetCSRFToken`: при `h.sessions == nil` вернуть `503 Service Unavailable`;
- в `checkCSRF`: при `h.sessions == nil` вернуть `false`;
- добавить два отрицательных теста на nil SessionStore.

### P1 — заявление о строгой Same-Origin-проверке для `GET /csrf` не соответствует коду

`GetCSRFToken` валидирует Origin и Referer только если они присутствуют. Запрос без обоих
заголовков принимается. Изменяющие endpoints реализованы строже и корректно требуют хотя
бы один из заголовков.

Варианты исправления:

- предпочтительно требовать Origin или Referer и на `/csrf`, затем проверить обычную
  работу UI во встроенных/старых браузерах Keenetic;
- либо явно документировать, что `/csrf` допускает отсутствие обоих заголовков, а защита
  опирается на валидную SameSite/session cookie и запрет CORS. Тогда формулировка
  «строгая Same-Origin-проверка» должна быть убрана.

Нужен тест `GET /csrf` без Origin/Referer с зафиксированным ожидаемым результатом.

### P1 — развёртывание названо безопасным, хотя применён `--force-overwrite`

В walkthrough действительно нет запрещённого `--force-reinstall`, но команда установки
содержит `--force-downgrade --force-overwrite`. Последний флаг принудительно разрешает
конфликт владения файлами пакетов и маскирует проблему состава IPK. Это особенно важно
для добавленных init-скриптов.

Что сделать:

1. Проверить владельцев конфликтующих файлов через `opkg search`/`opkg files`.
2. Добиться обычного `opkg install <ipk>` без `--force-overwrite`.
3. Если совместимость со сторонними telemt/tproxy пакетами обязательна — не включать их
   init-скрипты в основной IPK либо оформить явную миграцию/конфликты пакетов.

### P2 — backup manifest не проверяет записанный SHA-256

`preinst` сохраняет hash резервной копии, но `prerm` его не проверяет перед
восстановлением. В результате поле создаёт ложное ощущение контроля целостности.

Что сделать: перед восстановлением вычислить hash `.bak`, сравнить с manifest и при
несовпадении оставить оба файла на месте с предупреждением. Также записывать manifest
только после успешного `cp`.

### P2 — `GetCSRFSecret` возвращает внутренний изменяемый slice

Метод снимает mutex и отдаёт ссылку на внутренний массив. Текущий API-код его не меняет,
но контракт хрупкий. Возвращать копию (`bytes.Clone` или `append([]byte(nil), ...)`) либо
перенести вычисление токена внутрь сервиса.

### P2 — в `prerm` испорчена кодировка комментариев

Строки 66–70 и 84–85 отображаются mojibake. На выполнение shell это не влияет, но файл
сложно сопровождать. Пересохранить UTF-8 и заменить комментарии читаемым текстом.

## Что подтверждено по коду

- статический fallback `awgm-tgwebproxy` в проверенных исходниках не найден;
- серверный 32-байтный CSRF key создаётся через `crypto/rand`, хранится с режимом `0600`;
- mutating endpoints требуют Origin/Referer и динамический HMAC-токен;
- `randomHexSecret` и `generateTxID` возвращают ошибки вместо panic;
- `Service.Close()` останавливает timer/health worker и ждёт goroutine;
- readiness обычных TCP workers проверяет принадлежность сокета PID и работает fail-closed;
- init-скрипты маркированы `MANAGED_BY=awg-manager`, сверяют executable, точный путь
  конфигурации и starttime перед сигналами;
- unmanaged init-скрипты резервируются и восстанавливаются через manifest;
- frontend кэширует CSRF только в памяти, дедуплицирует запрос и делает один retry после
  CSRF-ошибки.

## Минимальный план завершения

1. Ротация скомпрометированных секретов и очистка walkthrough.
2. Fail-closed SessionStore и тесты.
3. Принять и зафиксировать строгую политику заголовков для `GET /csrf`.
4. Устранить необходимость `--force-overwrite`; проверить upgrade/remove на отдельной
   тестовой установке.
5. Добавить hash-проверку восстановления init-скриптов.
6. Повторить `go test ./internal/tgwebproxy/...`, API security tests, frontend checks и
   smoke-test на роутере без вывода секретов.

После пунктов 1–4 результат можно считать кандидатом для пользовательского тестирования;
