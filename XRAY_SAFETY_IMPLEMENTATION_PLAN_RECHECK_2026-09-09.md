План существенно доработан и закрывает основную часть замечаний из
`XRAY_SAFETY_FOUNDATION_REVIEW_2026-09-09.md`. Правильно выбраны следующие решения:

## Обязательные поправки

### 1. Карточка интеграции показывает только бинарник

Карточка `Xray-core` в `Настройки → Интеграции` должна содержать только:

- установлен или отсутствует бинарник;
- реальную версию ядра;
- кнопку `Скачать`, если бинарник отсутствует;
- кнопку `Удалить`, если бинарник установлен.

PID, состояние Xray-сервера, порт, клиенты, транспорт, CDN, ссылки и QR относятся к
`Серверы → Xray` и не должны дублироваться в интеграциях. Описание карточки:
`Ядро Xray-core для серверных и клиентских подключений`.

### 2. Запрещена фиктивная версия ядра

Если `xray version` завершился ошибкой или вывод не распознан, UI показывает
`Версия не определена`. Нельзя подставлять `26.7.28` или другую константу.

### 3. Безопасное удаление Xray-core

Нельзя безусловно выполнять `opkg remove xray-core` после автоматической остановки.
Удаление блокируется, если:

- включён Xray-сервер;
- существуют Xray-клиентские туннели;
- сервер или туннели используются политиками, правилами, proxy-группами или сервисными
  маршрутами.

UI должен показать все ссылки и предложить перейти к их настройке. Удаление бинарника не
удаляет серверные или клиентские конфигурации. Не использовать `--force-reinstall` и
другие принудительные флаги.

Installer должен учитывать происхождение бинарника: пакет opkg, управляемая загрузка или
внешняя установка. `opkg remove` допустим только для пакета, которым действительно
владеет opkg.

### 4. Единый путь бинарника

Сейчас используются `/opt/bin/xray` и `/opt/sbin/xray`. Нужен единый resolver, которым
пользуются:

- installer/status;
- Xray-сервер;
- будущий Xray client runtime;
- config validation;
- process identity.

Resolver выбирает канонический управляемый путь и поддерживает безопасное обнаружение
legacy-установки без запуска двух разных бинарников.

### 5. Полноценный readiness вместо фиксированных 200 мс

После `cmd.Start()` выполнять ограниченный по времени цикл, например до 2–3 секунд:

- обнаруживать ранний выход процесса;
- повторно подтверждать PID identity;
- для серверного runtime проверять открытие ожидаемого listener;
- сохранять PID record только после получения достаточного подтверждения запуска.

Ожидание ровно 200 мс не является гарантией успешного запуска.

### 6. Точный порядок транзакционного apply

Рекомендуемая последовательность:

```text
candidate
  → schema validation
  → render candidate
  → xray config test
  → snapshot previous settings/runtime/process state
  → stop previous owned process
  → atomically install candidate runtime
  → start candidate and perform readiness check
  → atomically save candidate settings
  → publish new in-memory state
```

При ошибке после остановки рабочего процесса необходимо:

```text
restore previous runtime
  → restore previous settings when required
  → restart previous process when it was running
  → verify rollback readiness
  → return the original error plus rollback status
```

Ошибка сохранения settings после успешного запуска кандидата также должна инициировать
rollback. Нельзя оставлять runtime и persisted settings разных ревизий.

Для выключенного кандидата config test не должен требовать установленного бинарника, но
schema validation и безопасное сохранение остаются обязательными.

### 7. Только обезличенные migration fixtures

Fixtures существующих роутеров должны сохранять структуру реальных конфигураций, но не
содержать реальные:

- IP-адреса;
- домены;
- UUID;
- пути доступа и токены;
- пользовательские названия устройств.

В репозитории используются только синтетические значения `example.com`, documentation IP
ranges и тестовые UUID. Полные исходные конфигурации роутеров не копируются в git, логи
или отчёты.

### 8. Проверка удаления старых маршрутов через основной mux

Недостаточно протестировать методы отдельного handler. Интеграционный тест должен собрать
тот же HTTP mux, который используется приложением, и подтвердить:

- старые `/api/xray/start`, `/stop`, `/restart`, `/config` не зарегистрированы;
- `/api/xray/status`, `/install`, `/uninstall` имеют строгие методы;
- `/api/servers/xray/*` остаётся единственным control plane Xray-сервера;
- CSRF/auth guard не обходится новыми маршрутами.

### 9. Нейтральное описание интеграции

Не использовать описание `серверное ядро для CDN-мостов`. Оно снова смешивает бинарник с
одним сценарием использования. Карточка должна называться и описываться нейтрально:

```text
Xray-core
Ядро для серверных и клиентских подключений
```

## Дополнительные уточнения

- `rawFields` объединять с typed schema так, чтобы канонические typed-поля всегда имели
  приоритет и неизвестные поля не могли подменить `enabled`, `clients` или пути.
- Backup migration создавать один раз на конкретную schema migration и не перезаписывать
  предыдущий рабочий backup.
- Ошибка чтения или разбора config должна сохранять оригинал и переводить сервис в
  recovery state, а не молча загружать пустые defaults.
- Проверку принадлежности процесса повторять непосредственно перед `SIGTERM` и перед
  `SIGKILL`.
- `GetConfig()` должен глубоко копировать все reference-типы, а не только текущий slice
  клиентов, чтобы будущие map/slice-поля не вернули mutable state наружу.
- Форматы Sing-box/Mihomo нельзя считать поддержанными по синтаксической корректности
  JSON/YAML: требуется проверка конкретной версией целевого ядра.

## Критерий допуска к реализации

План можно запускать после включения девяти обязательных поправок выше. После реализации
этап принимается только при одновременном выполнении условий:

1. В основном приложении существует один Xray server control plane.
2. Обычный restart AWG Manager не меняет persisted `Enabled`.
3. Невалидный candidate и ошибка запуска не меняют рабочую конфигурацию.
4. Xray runtime не может остановить другой Xray-процесс.
5. Интеграции управляют только бинарником, а сервер настраивается в `Серверы → Xray`.
6. Неподтверждённые клиентские форматы не выдаются пользователю.
7. Все новые тесты, frontend check и Linux ARM64 build проходят.
